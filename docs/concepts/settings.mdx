---
title: Settings
description: Declared, typed runtime settings resolved through one layered resolver (default, store, configuration pin), with secrets protected at rest and an IConfiguration projection.
---

Elarion's settings subsystem gives applications **runtime-changeable configuration**. Settings are **declared
once** as typed definitions; one **effective-value resolver** layers a default, a value stored at runtime and an
optional deployment-configuration pin; everything that reads settings — your code, the admin describe call, the
`IConfiguration` projection — goes through it. See
[ADR-0078](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0078-settings-definitions-and-effective-value-resolver.md)
(and [ADR-0011](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0011-runtime-settings-subsystem.md) for the store/change-source split).

<Callout type="info">
  Two backends ship: an **in-process** store (the zero-dependency default) and an **EF Core database**
  store (`Elarion.Settings.EntityFrameworkCore`). Change notification is in-process by default; add
  `Elarion.Settings.PostgreSql` (PostgreSQL `LISTEN/NOTIFY`) to propagate changes across all nodes.
  The EF Core store writes on your injected `DbContext`, so a `SetAsync`/`ResetAsync` made inside a transaction
  commits or rolls back with it — see [persistence & transactions](/docs/concepts/persistence-and-transactions).
</Callout>

## Declaring settings

A `static partial` class marked `[SettingDefinitions]` holds one `static partial SettingDefinition<T>` property
per setting. The attribute carries the key and metadata; a generator implements the property and verifies the
declarations at build time.

```csharp
[SettingDefinitions]
public static partial class AppSettings {
    [Setting("app:title", Default = "Untitled", Pinnable = true, Description = "The application title.")]
    public static partial SettingDefinition<string> Title { get; }

    [Setting("app:smtp", DefaultFactory = nameof(DefaultSmtp), Pinnable = true)]
    public static partial SettingDefinition<SmtpSettings> Smtp { get; }

    [Setting("app:smtp:password", Secret = true)]
    public static partial SettingDefinition<string> SmtpPassword { get; }

    [Setting("ui:theme", Scopes = ["global", "user"], Default = "light")]
    public static partial SettingDefinition<string> Theme { get; }

    private static SmtpSettings DefaultSmtp() => new() { Host = "localhost" };
}
```

| `[Setting]` option | Meaning |
| --- | --- |
| `key` | Hierarchical key with `:` separators; unique case-insensitively (it doubles as the `IConfiguration` key). |
| `Scopes` | Scope kinds the setting may be used in. Default: global only. |
| `Secret` | Protected at rest, never described, never projected into `IConfiguration`. No default allowed. |
| `Pinnable` | Deployment configuration may pin the value (global scope only). |
| `Default` / `DefaultFactory` | A constant for scalars, or a static factory (lazy, once) for records. |
| `Description` | Text for admin tooling. |

Build-time diagnostics: `ELSDEF001` invalid container (must be a top-level `static partial` class), `ELSDEF002`
invalid member, `ELSDEF003` invalid key, `ELSDEF004` duplicate key, `ELSDEF005` secret with a default,
`ELSDEF006` pinnable without the global scope, `ELSDEF007` invalid default.

Register the definitions on the host. `[assembly: UseElarion]` (or `[assembly: GenerateSettingDefinitionCatalog]`)
emits `ElarionSettingDefinitions.All`, aggregating this assembly and the public containers of referenced module
assemblies:

```csharp
builder.Services.ConfigureElarionJson(o => o.TypeInfoResolvers.Add(AppSettingsJsonContext.Default));
builder.Services.AddElarionSettings(o => o.AddDefinitions(ElarionSettingDefinitions.All));

[JsonSerializable(typeof(SmtpSettings))]
[JsonSerializable(typeof(string))]
internal sealed partial class AppSettingsJsonContext : JsonSerializerContext;
```

Values serialize through the canonical [`IElarionJsonSerialization`](/docs/capabilities/serialization) options —
source-generated `JsonTypeInfo<T>`, no reflection — so the value types must be in a JSON context.

An undeclared setting cannot be named: the manager takes definitions, not strings. A definition that is not
registered, or used in a scope it does not allow, throws `InvalidOperationException` (a programming error).

## Scopes

A setting belongs to a `SettingsScope`: `Global` (system-wide), `User(userId)`, or the `CurrentUser`
placeholder resolved against the ambient `ICurrentUser`. A scope is an open `(Kind, Owner)` value, so more kinds
can be added without changing the contracts or the store schema; a definition lists the kinds it allows.
User-scoped access **fails closed**: outside an authenticated context, `CurrentUser` throws rather than reading
global data.

## Reading and writing

```csharp
public sealed class SendEmailHandler(ISettingsManager settings) : IHandler<SendEmail, Result<Unit>> {
    public async ValueTask<Result<Unit>> HandleAsync(SendEmail request, CancellationToken ct) {
        var smtp = await settings.GetAsync(AppSettings.Smtp, cancellationToken: ct);
        var password = await settings.GetAsync(AppSettings.SmtpPassword, cancellationToken: ct);
        var theme = await settings.GetAsync(AppSettings.Theme, SettingsScope.CurrentUser, ct);
        // ...
        return Result.Success();
    }
}

var write = await settings.SetAsync(AppSettings.Title, "Inbox", cancellationToken: ct);
if (!write.IsSuccess && write.Error.Data is SettingWriteFailure { Reason: SettingWriteFailureReason.Pinned })
    // deployment configuration pins the title; the UI should show it read-only
```

`GetAsync` returns the **effective** value. `SetAsync` returns `Result<SettingWrite>` (the new version);
`ResetAsync` removes the stored value so the setting reverts to its default. Failures are typed
`AppError`s whose `Data` is a `SettingWriteFailure`: `Pinned` (a `BusinessRule` — the stored value would be
ignored) and `ConcurrencyConflict` (a `Conflict`). Concurrency is opt-in: an unconditional write is
last-write-wins; pass `expectedVersion` for optimistic concurrency.

## The effective-value resolver

`ISettingResolver` layers, lowest to highest:

1. the definition's **default** (`default(T)` when it declares none),
2. the **store** value,
3. a **configuration** value — only for `Pinnable` definitions in the global scope. A configuration value *pins*
   the definition: it wins, and writes are refused.

A configuration value pins only when it is present and neither empty nor whitespace, so a blank environment
variable or an unfilled template placeholder does not freeze a setting. Set
`o.EmptyConfigurationValuesPin = true` when an empty string is a legitimate pinned value.

The configuration text of a string setting is the string itself; any other type uses its JSON form (`2525`,
`true`, a JSON document such as `{"host":"mail"}` for a record), and bare words work for enums and string-like
types. A malformed pinned value fails loudly on read. Only non-projection configuration providers are consulted
(see below), so the projection cannot pin.

## Secrets

Definitions with `Secret = true` are protected at rest through an `ISettingValueProtector`. Add the Data
Protection implementation:

```csharp
builder.Services.AddElarionSettingsDataProtection();   // Elarion.Settings.DataProtection
```

- The payload is bound to scope kind, owner and key (renaming a secret key requires writing it again).
- The protection **scheme** is store metadata — `SettingEntry.Protection`, the nullable `protection` column on
  the EF row — not a prefix inside the value. Add the column to an existing table with a migration.
- **Fail closed:** a secret definition with no `ISettingValueProtector` registered fails host startup. There is
  no unprotected fallback; development hosts use Data Protection's default key ring.
- `DescribeAsync` never returns a secret's value, and secrets are never projected into `IConfiguration` (it is
  routinely bound, logged and dumped). Read secrets through `ISettingsManager`.
- `ISettingReprotector.ReprotectAsync(scope, prefix?)` converges legacy plaintext, rotated keys and older
  schemes; it is idempotent and version-guarded. `AddElarionSettingsDataProtection` also runs it once at start
  for the global scope (`ReprotectOnStartup`).
- Persist and share the Data Protection key ring in production; a lost key ring makes protected settings
  unrecoverable.

## Describing settings for an admin UI

```csharp
IReadOnlyList<SettingDescription> all = await settings.DescribeAsync(cancellationToken: ct);
```

Each entry has `Key`, `ValueType`, `Scope`, `AllowedScopes`, `IsSecret`, `IsPinnable`, `IsPinned`, `HasValue`,
`Source` (`Default`, `Store` or `Configuration`), `ValueJson` (never for secrets), `Version` (usable as
`expectedVersion`), `IsUnreadable` (a stored secret that cannot be decrypted) and `Description`. Elarion ships
no handlers for it; map it to whatever your host exposes.

## Watching for changes

`ISettingsManager.Watch(definition)` and `Watch(prefix)` return an `IChangeToken` that fires when the effective
value may have changed: a store change, or — for pinnable global definitions — a deployment-configuration
reload. Tokens are one-shot; re-watch or use `ChangeToken.OnChange`.

```csharp
ChangeToken.OnChange(
    () => settings.Watch(AppSettings.Smtp),
    () => _logger.LogInformation("SMTP settings changed; reloading."));
```

## Using the EF Core database store

`Elarion.Settings.EntityFrameworkCore` persists settings to a relational database via your `DbContext`:

```csharp
// In your DbContext's OnModelCreating:
modelBuilder.UseElarionSettings();   // maps the elarion_settings table

// In Program.cs (replaces the in-process store):
builder.Services.AddElarionSettingsEntityFrameworkCore<AppDbContext>();
```

Writes are change-tracker-free and immediate (they never flush the caller's unrelated tracked changes),
with a `version` column backing optimistic concurrency. Generate and apply an EF migration for the
`elarion_settings` table; the framework ships no migrations.

**Database providers.** The store is provider-neutral EF Core: table and column names are resolved from your
model, and the two raw statements it issues (the create-path `INSERT` and the last-write-wins
`UPDATE … RETURNING`) are built from that model rather than hard-coded for one dialect. **PostgreSQL and
SQLite are both exercised by the test suite**; any relational provider whose SQL supports `RETURNING` should
behave the same (SQLite has supported it since 3.35 — every bundled `Microsoft.Data.Sqlite` native build is
far newer). On SQLite, pair the store with the default in-process change source: a SQLite database file
implies a single application node, and in-process notification already reaches every watcher in that process.
The multi-node change source below is deliberately PostgreSQL-only — with SQLite there is no second node to
notify.

**Change notification and transactions.** A store write enlists in the context's ambient transaction when one
is open, and the default in-process notifier is **commit-gated** to match: a write made *outside* a transaction
is announced immediately (it is already durable), while a write made *inside* a caller-owned transaction is
deferred and announced only when that transaction commits — and dropped on rollback, so a watcher never reloads
a value a rollback discards. This works out of the box — `AddElarionSettingsEntityFrameworkCore<TContext>`
auto-attaches an EF Core transaction interceptor to `TContext` — so single-node live reload of
`IConfiguration`/`IOptionsMonitor<T>` and the scheduler applies as soon as the command that changed the setting
commits (a setting changed from a command handler no longer needs a restart to take effect). The one thing
the in-process notifier cannot do is cross process boundaries; the PostgreSQL change source below extends the
same commit-gated delivery to **every** node.

**Single-instance notification.** With only the shipped in-process source, a settings change on one node is
not observed by another node's watchers or scheduler until that node restarts. When the EF Core store is
paired with the in-process source, `AddElarionSettingsEntityFrameworkCore` registers a startup service that
logs a **Warning** making this limitation visible at runtime; registering the PostgreSQL source below silences
it. In a deliberately single-node deployment — a SQLite-backed host, say — the warning is informational and
safe to ignore: there is no other node whose watchers could go stale.

## Multi-node change notification (PostgreSQL LISTEN/NOTIFY)

`Elarion.Settings.PostgreSql` makes change notification cross-instance over the database the settings already
live in — no extra infrastructure:

```csharp
// In Program.cs, next to the EF Core store (either order):
builder.Services.AddElarionSettingsEntityFrameworkCore<AppDbContext>();
builder.Services.AddElarionPostgreSqlSettingsChanges(connectionString);
// or, if the host already manages an NpgsqlDataSource:
builder.Services.AddElarionPostgreSqlSettingsChanges(dataSource);
```

A write on any node now fires `IChangeToken` watchers on **every** node — `ISettingsManager.Watch`, the
settings `IConfiguration` projection, `IOptionsMonitor<T>`, and the scheduler's `${...}` live rescheduling all
follow. How it works:

- A hosted listener holds one dedicated `LISTEN` connection per node and fires the matching watch tokens for
  each received notification, reconnecting with exponential backoff if the connection drops. PostgreSQL does
  not queue notifications for absent listeners, so after a reconnect the listener fires **all** watches — a
  spurious re-read is cheap and always converges.
- Watch tokens fire **only** from the notification loop: a local write loops back through the database like a
  remote one, so every node — including the writer — observes changes in commit order through one path.
- The EF Core store's writes are announced with `pg_notify` **on the store's own connection**, which
  PostgreSQL makes transactional: a write inside a caller-owned transaction is announced only when that
  transaction commits, and never on rollback. Transactional writes are therefore fully notified with this
  backend.
- The channel (`elarion_settings_changed` by default) and the reconnect backoff are configurable via
  `PostgreSqlSettingsChangeOptions`; two applications sharing one database should use distinct channels.

The store's `DbContext` must target the same PostgreSQL database as the connection string / data source given
to `AddElarionPostgreSqlSettingsChanges`. See
[ADR-0024](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0024-postgres-listen-notify-settings-changes.md) for the design and alternatives.

`UseElarionSettings` (which also maps the nullable `protection` column) takes optional `tableName` and `schema` parameters to rename the table or place it in
a non-default schema, plus a `snakeCase` toggle (default `true`; `false` switches to PascalCase names — the
default table becomes `ElarionSettings`): `modelBuilder.UseElarionSettings("app_settings", "app")`.

On a `[GenerateDbSets]` context you can skip the hand-written call: annotate the context with
`[GenerateElarionSettings]` (optionally with `SnakeCase`/`TableName`/`Schema`) and the bundled generator
emits the `DbSet<Setting>` and applies the same model configuration through the EF generator's model-config
seam (`ELSET001` if `[GenerateDbSets]` is missing).

## IConfiguration projection

`Elarion.Settings.Configuration` projects the resolver's effective **global** values into `IConfiguration` with
live reload, for `IOptionsMonitor<T>` and the scheduler's `${...}` variable substitution:

```csharp
builder.AddElarionSettingsConfiguration();   // after the other configuration sources
```

It is a **projection, not a second source of truth**: it is derived from the resolver and the resolver never reads
it back, so it cannot pin a definition and there is no store-versus-configuration precedence switch. Scalar
definitions become one key; object values are flattened to `key:property` (and `key:0`, `key:1` for arrays) so a
section binds to your options type. Secrets are never projected, values pinned by configuration are skipped (they
are already there), and only the global scope is surfaced. Register it after your other sources so a later
provider does not mask the projected effective value.

Because `IConfiguration` is built before the DI container, the background refresher performs the initial load in
its `StartAsync`, before later-registered hosted services (notably the scheduler) start. The load is time-bounded
so a slow store cannot hang startup. The refresher reprojects on store changes and when the rest of the
configuration reloads (a pin may have appeared); the provider reloads only when its data actually changed.

## Scheduler integration

Settings flow into the scheduler through [variable substitution](/docs/concepts/variable-substitution): a job's
`${...}` schedule variables resolve from the (config-backed) variable source, and the settings
`IConfiguration` adapter is observable, so changing a setting **reschedules affected recurring jobs live**
(not just on their next fire). No scheduler-specific wiring is needed.

## Roadmap

The foundation, the EF Core database store, the `IConfiguration`/`IOptionsMonitor` adapter, the scheduler
integration, and the cross-instance PostgreSQL `LISTEN/NOTIFY` change source ship today. A Redis pub/sub
change source is a possible future provider over the same contracts. See
[ADR-0011](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0011-runtime-settings-subsystem.md) for the full design and phasing and
[ADR-0024](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0024-postgres-listen-notify-settings-changes.md) for the multi-node backend.
