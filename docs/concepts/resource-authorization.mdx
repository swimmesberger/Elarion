---
title: Resource authorization
description: Per-resource (read/write) access control and efficient database-level filtering — owner, tenant, and role-based sharing — composed from one declarative source.
---

[Handler authorization](/docs/concepts/authorization) decides on the *whole operation* ("may this user call this handler?").
**Resource authorization** decides on *specific resources* ("may this user read *this* contact?", "*which*
contacts may they list?"). These are two different problems, and Elarion solves them with two complementary,
opt-in legs driven from one declarative source — never by filtering rows in memory after the query (which
breaks pagination and leaks data).

<Callout type="info">
  Resource authorization is transport-neutral and depends only on `ICurrentUser` (user id + roles). The
  database is the only external system — there is no relationship/policy-engine dependency.
</Callout>

## Two questions, two legs

| Question | Leg | Mechanism |
|---|---|---|
| "Which resources may I read?" (lists/search) | **List filter** | `[ResourceFilter<T>]` → a predicate pushed into SQL **before** paging |
| "May I read/write *this* resource?" (get-one/write) | **Point check** | `[RequireResource(...)]` → the `IResourceAuthorizer` seam, answered from the same filter |

Both legs read **one rule per entity**: the registered `IQueryAuthorizer<T>`. The list composes it into the query,
the point check asks whether one row is in it, and [the complement](#rows-hidden-from-the-caller) negates it.

## Leg B — list filtering (push the rule into SQL)

Declare a filter for an entity on a dedicated partial class (the entity stays clean, like `[Keyset<T>]`):

```csharp
[ResourceFilter<Contact>(
    OwnerProperty = nameof(Contact.OwnerId),     // a grant: the row's owner
    TenantProperty = nameof(Contact.TenantId),   // a scope: must match the caller's tenant claim
    Shared = true, ResourceTypeName = "Contact")] // a grant: shared via the grants table (user or role)
public sealed partial class ContactAccess;
```

The generator completes the class as an `IQueryAuthorizer<Contact>` and auto-registers it. Inject it into the
handler and compose it into the query **before** paging:

```csharp
public sealed class ListContacts(AppDbContext db, ICurrentUser user, IQueryAuthorizer<Contact> access)
    : IHandler<ListContacts.Query, Result<Page<ContactDto>>> {

    public async ValueTask<Result<Page<ContactDto>>> HandleAsync(Query request, CancellationToken ct) =>
        await db.Contacts
            .WhereAuthorized(access, user)                           // owner OR shared-with-user OR shared-with-role
            .Where(c => c.Category == request.Category)             // your business filters
            .ToKeysetPageAsync(request, RecentContacts.Definition, c => new ContactDto(c.Id), cancellationToken: ct);
}
```

The predicate is part of the single SQL statement, so the database filters the rows — pagination and total
counts are correct, and unauthorized rows are never returned. The rules compose as **`AND(scopes) AND
OR(grants)`**: a row is visible when it satisfies every scope (tenant) and at least one grant (owner, or a share).

In plain terms, the `Shared` flag decides **how wide the list is**:

- **`Shared = false`** (owner/tenant rules only) — the caller sees **only the rows they own**, within their tenant.
- **`Shared = true`** — the caller *also* sees **rows explicitly shared with them**, either directly or with a
  role they belong to, recorded in the [grants table](#sharing-with-users-and-roles).

Either way, a row the caller neither owns nor was granted is never returned — and never counted.

<Callout type="info">
  **Inject the authorizer; the static `Specification` is a shortcut for field-only filters.** A filter that uses
  `Shared` consults the grants table, so it is a **scoped service** — you must inject `IQueryAuthorizer<Contact>`
  (as above), and there is no static accessor. A filter with only field rules
  (`OwnerProperty`/`TenantProperty`) is stateless, so the generator *also* exposes a static
  `ContactAccess.Specification` singleton you can hand to `WhereAuthorized` without DI. Both forms are
  auto-registered as `IQueryAuthorizer<Contact>` by the host bootstrapper (module-feature-gated), so injection
  works for either.
</Callout>

<Callout type="warn">
  Never filter a list in memory after the query (the `@PostFilter` shape). It returns short pages, wrong
  counts, and leaks how many rows exist. `WhereAuthorized` exists precisely so you don't.
</Callout>

<Callout type="warn">
  **`WhereAuthorized` is convention-only — nothing attaches it for you.** Unlike `[RequirePermission]` or
  `[RequireResource]`, which the generator auto-attaches as decorators, the list filter runs only where a
  handler composes it into the query. A list handler that forgets `WhereAuthorized` (or applies it after a
  `.Select()` projection that discards the entity) returns **every** row — the classic BOLA/IDOR shape.
  Treat "every list query over an access-controlled entity starts with `WhereAuthorized`" as a review
  checklist item, and cover each list handler with a test asserting an unshared row is absent.

  This is the right trade for *sharing*, where the decision is per feature. It is the wrong trade for
  *tenancy*, where a forgotten call is a cross-tenant leak rather than a widened list — so tenancy gets
  its own unconditional mechanism. See [multi-tenancy](/docs/capabilities/multi-tenancy).
</Callout>

### Administrators: a bypass permission

"Holds `contacts.manage`, sees every contact" is one property: `BypassPermission`. For a caller with that permission
claim the owner and sharing rules are lifted; everyone else gets the declared rules. **The scope stays:** with a
`TenantProperty`, the holder sees every contact of their own tenant, never another tenant's, and a caller without a
tenant claim still sees nothing. Only a filter with no scope rule becomes unrestricted.

```csharp
[ResourceFilter<Contact>(OwnerProperty = nameof(Contact.OwnerId), Shared = true, ResourceTypeName = "Contact",
    BypassPermission = "contacts.manage")]
public sealed partial class ContactAccess;
```

The permission is read from the `permission` claim, the default of `AuthorizationOptions.PermissionClaimType`; set
`PermissionClaimType` on the attribute when the host changes it. Where the administrators are a **role** rather than
a permission, `BypassRole = "Admin"` does the same; with both set, either one bypasses.

The bypass is part of the filter, so the point check sees it too once the entity's
[filter check](#one-rule-for-the-list-and-the-point-check) is registered. The grants-only point check knows neither
the owner column nor the bypass.

### Data that belongs to a resource

Notes, files and comments point at a resource by id and are visible exactly when that resource is. Filter them by
their **owner's** visibility instead of re-implementing it for each table — `WhereAuthorizedVia` runs the owner's
filter as a subquery of the same statement (`WHERE contact_id IN (SELECT id FROM contacts WHERE …)`):

```csharp
var notes = await db.Notes
    .Where(n => n.OwnerKind == RecordKind.Contact)
    .WhereAuthorizedVia(n => n.OwnerId, db.Contacts, c => c.Id, contactAccess, currentUser)
    .ToOffsetPageAsync(request, n => new NoteRow(n.Id, n.Text), NoteSort, ct: ct);
```

**Narrow a shared pointer to one owner kind first.** When `OwnerId` points at contacts, properties and invoices
alike, the `OwnerKind` filter above is mandatory, not an optimization: without it, a note on an invoice whose id
equals a visible contact's id passes. For data whose owners are of several kinds, filter each kind's rows by its own
owner and combine the queries (`Concat`) before paging. A nullable pointer works with an owner key of the same type
(`c => (Guid?)c.Id`); rows pointing at no owner are then excluded.

#### Visible through an owner, as part of a rule

`WhereAuthorizedVia` filters one query. When "readable through an owner" is one **alternative** of a type's rule —
an e-mail is visible to its sender, and to whoever may read a record it is assigned to — state it with
`QueryAuthorizers.Via`, so it composes with the other alternatives and the [inverse](#who-may-see-a-record) can read
it. The owner type's own rule, composed or generated, is used as it stands:

```csharp
// Owners reached by a navigation, or a join through a link table: a static rule.
public static readonly IQueryAuthorizer<Email> Visibility = QueryAuthorizers.AnyOf(
    QueryAuthorizers.ForUser<Email, Guid>((email, userId) => email.SenderId == userId),
    QueryAuthorizers.Via<Email, Contact>(
        email => email.Links.Select(link => link.Contact), ContactVisibility.Authorizer));

// Owners behind a (kind, id) pointer, which has no navigation: one EXISTS per owner kind, over its set.
services.AddScoped<IQueryAuthorizer<Email>>(sp => {
    var db = sp.GetRequiredService<AppDbContext>();
    return QueryAuthorizers.AnyOf(
        QueryAuthorizers.ForUser<Email, Guid>((email, userId) => email.SenderId == userId),
        QueryAuthorizers.Via<Email, Contact>(
            db.Contacts,
            (email, contact) => email.Links.Any(l => l.Kind == RecordKind.Contact && l.RecordId == contact.Id),
            ContactVisibility.Authorizer),
        QueryAuthorizers.Via<Email, Property>(
            db.Properties,
            (email, property) => email.Links.Any(l => l.Kind == RecordKind.Property && l.RecordId == property.Id),
            PropertyVisibility.Authorizer));
});
```

- **A row needs an owner.** A row with none is not visible through `Via`, also to a caller the owner's rule does not
  restrict — unlike `WhereAuthorizedVia`, which keeps every row for such a caller. Give unassigned rows an alternative
  of their own.
- **Narrow a shared pointer to the owner's kind** in the join, as above, for the reason given for `WhereAuthorizedVia`.
- **The set form belongs to a scope.** `db.Contacts` becomes part of every query the rule filters, so compose that
  rule where the context lives — a scoped registration — not in a static field.
- **The owner is asked about the row's operation.** Pass `ownerOperation: ResourceOperation.Read` to let whoever may
  read the record also change what is assigned to it.

### Composing filters: membership tables and computed rules

A rule the attribute cannot express — sharing through an application-owned membership table (contact groups), rows
every holder of a permission may see — is **added to** the generated filter, not written instead of it.
`QueryAuthorizers` has the building blocks; the result is still a single predicate the database evaluates:

```csharp
// The owner rule, as a building block: generated, but not registered.
[ResourceFilter<Contact>(OwnerProperty = nameof(Contact.OwnerId), Register = false)]
public sealed partial class ContactOwnerFilter;

public static class ContactVisibility {
    public static readonly IQueryAuthorizer<Contact> Authorizer = QueryAuthorizers.AnyOf(
        // administrators see every contact
        QueryAuthorizers.WhenRole("Admin", QueryAuthorizers.Unrestricted<Contact>()),
        // whoever may read contacts sees the ones nobody restricted
        QueryAuthorizers.WhenPermission("contacts.read", QueryAuthorizers.Rows<Contact>(c => !c.IsRestricted)),
        // the owner
        ContactOwnerFilter.Specification,
        // members of a group the contact is shared with
        QueryAuthorizers.ForUser<Contact, Guid>((c, userId) =>
            c.Shares.Any(share => share.Group.Members.Any(member => member.UserId == userId))));
}

// A module's ConfigureServices, or the host: this is the IQueryAuthorizer<Contact>.
services.AddSingleton(ContactVisibility.Authorizer);
```

| Building block | Grants |
|---|---|
| `Rows(predicate)` | the rows matching the predicate |
| `Unrestricted()` | every row (a `null` filter) |
| `ForUser<TEntity, TKey>((row, userId) => …)` | the rows related to the caller's id — ownership, membership, an assignment |
| `When(condition, then)` / `WhenPermission(permission, then)` / `WhenRole(role, then)` | `then`, to callers passing the gate |
| `ForOperations(authorizer, operations…)` | `authorizer`, for the listed operations only |
| `Via(owners, ownerRule)` / `Via(ownerSet, joins, ownerRule)` | the rows with an owner `ownerRule` grants ([through an owner](#visible-through-an-owner-as-part-of-a-rule)) |
| `AnyOf(…)` / `AllOf(…)` | the union / the intersection |
| `From((user, operation) => …)` | whatever the delegate returns — **unchecked** |

**They fail closed.** Every building block denies a caller who is not authenticated before the rule is consulted,
and `ForUser` also denies a caller whose id does not parse as `TKey`, so no alternative repeats that preamble.
`From` is the exception: its delegate is the whole rule, including the authentication check. `ForUser` takes the
rule as one expression over the row and the caller's id; the id reaches the database as a parameter.

**Register the composition, not its parts.** `Register = false` keeps a building block out of the container. The
generated registration is a `TryAdd` in any case, so an `IQueryAuthorizer<T>` you register yourself — in a module's
`ConfigureServices`, or in the host before or after `AddElarion` — is the one an injected authorizer and the point
check resolve. Two registered `[ResourceFilter]` classes for one entity are reported as
[`ELMOD007`](/docs/reference/diagnostics). A filter with `Shared` is a scoped service, so compose it in a factory:
`services.AddScoped<IQueryAuthorizer<Contact>>(sp => QueryAuthorizers.AnyOf(new ContactAccess(sp.GetRequiredService<IResourceGrantSource>()), …))`.

<Callout type="warn">
  **A scope does not survive an OR.** `AnyOf(tenantScopedFilter, groupRule)` lets `groupRule` reach rows of every
  tenant, and an `Unrestricted()` alternative lifts the scope for its callers. Keep the scope outside the
  alternatives — `QueryAuthorizers.AllOf(scope, QueryAuthorizers.AnyOf(…))`, where an unrestricted alternative is
  neutral — or leave tenancy to [ambient tenant scoping](/docs/capabilities/multi-tenancy), which no composition can
  lift.
</Callout>

#### Wider for reading than for writing

`ForOperations` states which operations an alternative grants; every other operation is denied for it:

```csharp
QueryAuthorizers.AnyOf(
    QueryAuthorizers.ForOperations(                       // reading only
        QueryAuthorizers.WhenPermission("contacts.read", QueryAuthorizers.Rows<Contact>(c => !c.IsRestricted)),
        ResourceOperation.Read),
    ContactOwnerFilter.Specification)                     // every operation
```

`WhereAuthorized` asks about **`Read` unless told otherwise**. With a rule like this one, a write handler must pass
its operation (`WhereAuthorized(access, user, ResourceOperation.Update)`) or declare it on `[RequireResource]`, which
passes it for you.

### Rows hidden from the caller

A document registry that subtracts the hidden rows of several record kinds needs the **complement** of a filter.
`WhereNotAuthorized` is that, as a query — nothing for an unrestricted caller, everything for a caller the rule
denies entirely:

```csharp
var hiddenContactIds = db.Contacts.WhereNotAuthorized(ContactVisibility.Authorizer, currentUser).Select(c => c.Id);
var files = db.Files.Where(f => f.ContactId == null || !hiddenContactIds.Contains(f.ContactId.Value));
```

The two sets partition the source under Entity Framework Core's default null semantics; with `UseRelationalNulls` a
predicate that evaluates to SQL `NULL` puts its row in neither.

## Sharing with users and roles

Shares live in a DB-native grants table. Map it on your context — either with the attribute (emits the `DbSet`
and the table mapping, like `[GenerateElarionIdentity]`):

```csharp
[GenerateDbSets]
[GenerateElarionResourceGrants]
public sealed partial class AppDbContext(DbContextOptions<AppDbContext> options) : DbContext(options) {
    protected override void OnModelCreating(ModelBuilder modelBuilder) => ConfigureEntities(modelBuilder);
}
```

…or by hand: `modelBuilder.ApplyElarionResourceGrants()`. Both forms take the same overrides — the attribute
accepts optional `TableName` and `Schema` properties alongside `SnakeCase`, and
`ApplyElarionResourceGrants(tableName, schema, snakeCase)` mirrors them (defaults `elarion_resource_grants`,
or `ElarionResourceGrants` with `snakeCase: false`; the principal index name is derived from the table name —
`ix_{table}_principal` / `IX_{table}_Principal`). Then register the backend and manage shares:

```csharp
services.AddElarionResourceAuthorization<AppDbContext>();   // grants source, store, and the point-check authorizer
```

Shares are managed through the injected `IResourceGrantStore`:

```csharp
[Handler]
public sealed class ShareContact(IResourceGrantStore grants) {
    public async ValueTask<Result> HandleAsync(ShareContactCommand command, CancellationToken ct) {
        // Share one contact with the "Hausmeister" role for read — every user in that role can now see it.
        await grants.GrantAsync(
            new ResourceGrant("Contact", command.ContactId.ToString(),
                ResourcePrincipal.Role("Hausmeister"), ResourceOperation.Read), ct);
        return Result.Success();
    }
}
```

The `Shared` filter turns this into an indexed correlated `EXISTS` over the caller's user id **or any of their
roles** — a small, bounded lookup that scales.

Granting the same `(resource, principal, operation)` twice is **idempotent** — the EF Core backend claims a grant
with an `INSERT … ON CONFLICT DO NOTHING`, so a concurrent duplicate never raises a unique violation (which would
otherwise abort, and poison, the caller's ambient transaction). The resource-type discriminator, resource id,
user ids, and role names are matched **case-sensitively** (`StringComparison.Ordinal`): a casing mismatch between a
stored grant and the caller's `ICurrentUser` fails closed (denies) — it never grants access. Store principal ids
and role names in a consistent casing.

Grants are **operation-scoped**, and the `Shared` rule only matches grants for the operation `WhereAuthorized`
asks about — which **defaults to `Read`**. To list the rows a caller may *edit*, pass the operation explicitly:

```csharp
db.Contacts.WhereAuthorized(access, user, ResourceOperation.Update)   // EXISTS matches "update" grants
```

The operation narrows only the **grant** (`Shared`) lookup; the `OwnerProperty`/`TenantProperty` rules are
operation-independent, so an owner still sees their own rows under any operation.

## Leg A — the per-resource point check

For a get-one or write handler, declare which request property names the resource. The id is a **compile-checked
path** (per [ADR-0012](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0012-dynamic-variable-references.md)), not a string expression — the
generator validates it against the request and emits a zero-reflection accessor:

```csharp
[RequireResource(typeof(Contact), Operation = "read", Id = nameof(GetContact.Query.Id))]
public sealed class GetContact : IHandler<GetContact.Query, Result<ContactDto>> {
    public sealed record Query : IQuery { public Guid Id { get; init; } }
    // ...
}
```

The decorator resolves the id and asks `IResourceAuthorizer`.

### One rule for the list and the point check

Register a **filter check** for the entity, and its point check asks the same `IQueryAuthorizer<T>` the list uses —
one `EXISTS` for the row with that key, among the rows the rule lets the caller access for the declared operation:

```csharp
services.AddElarionResourceFilterCheck<AppDbContext, Contact, Guid>(c => c.Id);

[RequireResource(typeof(Contact), Operation = "update", Id = nameof(Command.Id), DenyAs = ResourceDenial.NotFound)]
public sealed class UpdateContact : IHandler<UpdateContact.Command, Result> { /* ... */ }
```

Owner, sharing, bypass and every composed alternative apply, because it is the registered authorizer that is asked —
an administrator who sees a contact in the list passes its get-one, and a caller who may read but not change a
record is denied the update. It needs `Elarion.Authorization.EntityFrameworkCore`, but not the grants table.

- **A row that does not exist is denied**, also for an unrestricted caller. With `DenyAs = ResourceDenial.NotFound`
  a hidden record and a missing one get the same answer.
- **The set's query filters apply**: a soft-deleted row is denied, and ambient tenant scoping holds. To keep a hidden
  record authorized for the accounts that could see it (a restore command), shape the set:
  `AddElarionResourceFilterCheck<AppDbContext, Contact, Guid>(c => c.Id, rows => rows.IgnoreQueryFilters(["SoftDelete"]))`.
  Name the filter you drop — a bare `IgnoreQueryFilters()` drops the tenant filter with it.
- **The request's id** may be the key type or, for `Guid`/`int`/`long` keys, its text. An id that cannot be the
  entity's key is denied.
- The check is for an **existing** record. Guard a create with `[RequirePermission]`.

A resource type **without** a filter check is authorized from the grants table (a share with the caller's user or
roles) once `AddElarionResourceAuthorization` is called; with no backend registered the check **fails closed** (a
logged 403). The filter check is registered per entity: a `[RequireResource]` on a type that has a filter but no
check is answered by the grants alone — it denies more, never less.

A hand-written check for one type is a keyed service: `services.AddKeyedScoped<IResourceAuthorizer, InvoiceAuthorizer>(typeof(Invoice))`.

### Hidden, not forbidden

A `403` tells the caller the record exists. When a list filter hides records, their point check should answer like a
missing record instead — otherwise ids can be probed one by one:

```csharp
[RequireResource(typeof(Contact), Id = nameof(GetContact.Query.Id), DenyAs = ResourceDenial.NotFound)]
public sealed class GetContact : IHandler<GetContact.Query, Result<ContactDto>> { /* ... */ }
```

A denial now answers `404` with the code `not_found` and `AuthorizationOptions.ResourceNotFoundMessage` (default
"The requested resource was not found."); make the handler's own missing-record answer use the same message, or the
two stay distinguishable. `not_found` joins the operation's declared error contract. With several `[RequireResource]`
on one handler, they are checked in declaration order and the first denial answers with its own `DenyAs`, so declare
the hidden resource first when a later, forbidden one would confirm it exists.

### The resource-type discriminator

A grant identifies its resource by a **discriminator string**, stored in the `resource_type` column. The point
check derives that discriminator from `typeof(Contact)` — by default the type's **`FullName`** (e.g.
`MyApp.Crm.Contact`), so two entities named `Contact` in different modules never share authorization. Every path
that produces or compares the discriminator agrees on it via
`Elarion.Abstractions.Authorization.ResourceTypeDiscriminator`:

- what `IResourceGrantStore.GrantAsync` **writes** (the `ResourceGrant.ResourceType` string you pass),
- the point check in the grants-backed `IResourceAuthorizer`, and
- the `EXISTS` subquery the `[ResourceFilter(Shared = true)]` generator emits.

When you want a **stable, namespace-independent** discriminator (e.g. the short `"Contact"`), set the same
override on all three: `[RequireResource(typeof(Contact), ResourceTypeName = "Contact")]`,
`[ResourceFilter<Contact>(Shared = true, ResourceTypeName = "Contact")]`, and the `ResourceType` string on every
`ResourceGrant` you write. If they disagree, the grant simply never matches (fail-closed).

## The escape hatch — validate before a write

A handler that loads the record anyway can authorize and load in **one statement**, by the same rule — the
deliberate alternative to a hidden write interceptor, and one round trip less than `[RequireResource]`:

```csharp
var contact = await db.Contacts
    .WhereAuthorized(access, currentUser, ResourceOperation.Update)
    .FirstOrDefaultAsync(c => c.Id == request.Id, ct);
if (contact is null)
    return AppError.NotFound("The requested resource was not found.");   // hidden and missing answer alike
```

Or inject `IResourceAuthorizer` for a check by id without loading; it routes like `[RequireResource]` does (the
entity's filter check, else the grants):

```csharp
if (!await resourceAuth.AuthorizeResourceAsync(
        new ResourceAuthorizationContext(currentUser, typeof(Contact), "Contact", ResourceOperation.Update, request.Id), ct))
    return Result.Failure(AppError.Forbidden("Not allowed to update this contact."));
```

`IQueryAuthorizer<T>.Matches(entity, user)` evaluates the predicate in memory against a loaded entity. Use it only
for rules that read the entity's own scalar fields (owner, tenant): a navigation the entity was loaded without is
empty there, which denies a positive rule and **allows** a negated one.

<Callout type="info">
  `[ResourceFilter]` predicates are a **read** filter; they do not stop a wrong-owner *write*. Enforce writes
  with `[RequireResource]` or the escape hatch above. Raw SQL (`FromSqlRaw`) and `IgnoreQueryFilters` bypass the
  in-app predicate — there is no Postgres RLS backstop, so keep enforcement in your handlers.
</Callout>

## Who may see a record?

Mentions, notifications and an access overview ask the inverse question: *which* principals may access record X.
`WhereAuthorizedFor` answers it from the same rule the list filter applies, in one statement:

```csharp
// The active staff accounts that may read this contact.
var readers = await users.ActiveStaff(now)                       // the candidates: your eligibility rule
    .WhereAuthorizedFor(db.Contacts.Where(c => c.Id == contactId), contactAccess, directory)
    .ToListAsync(ct);
```

- **The candidates are yours.** The result is a subset of the principal ids you pass, so you decide who is eligible at
  all (the accounts that can still sign in, the staff of one department) and the rule decides who among them may
  access the rows. With several rows, a principal is returned when it may access at least one.
- **The rule is read as a relation** between a row and a principal id. `ForUser` already is one; `Rows`,
  `Unrestricted`, `WhenPermission`, `WhenRole`, `ForOperations`, `Via`, `AnyOf`, `AllOf` and the generated `[ResourceFilter]`
  (owner, bypass permission and role, user and role grants) translate to one. Pass the operation to ask who may
  *change* the record.
- **Complete or refused.** A rule that contains `QueryAuthorizers.From`, `QueryAuthorizers.When`, a hand-written
  authorizer or a generated filter with a `TenantProperty` throws `NotSupportedException` naming that part — it
  never answers for the rest and leaves an alternative out. Restate the part with the building blocks, or implement
  `IPrincipalQueryAuthorizer<T>` on your authorizer.

### The principal directory

A gate such as "holds `contacts.read`" is read from the live `ICurrentUser` when a caller lists contacts. For the
inverse there is no caller, so the same fact comes from an `IPrincipalDirectory<TKey>`: two queries, the roles and
the **effective** claims (a role's claims listed for each member) of every principal.

```csharp
// ASP.NET Core Identity tables: user_roles, user_claims and the role_claims of a principal's roles.
services.AddElarionIdentityPrincipalDirectory<AppDbContext, ApplicationRole, Guid>();
```

<Callout type="warn">
  **The directory must agree with the principal your host builds.** The Identity-backed directory mirrors Identity's
  default claims factory. If the host adds a role or a claim at sign-in or per request — an instance owner who is made
  an administrator on every request — register your own directory that adds the same fact, or those principals are
  missing from the answer:

  ```csharp
  public sealed class AppPrincipalDirectory(AppDbContext db) : IPrincipalDirectory<Guid> {
      private readonly IdentityPrincipalDirectory<AppDbContext, ApplicationRole, Guid> _stored = new(db);

      public IQueryable<PrincipalRole<Guid>> Roles => _stored.Roles.Concat(
          db.Users.Where(u => u.IsOwner).Select(u => new PrincipalRole<Guid> { PrincipalId = u.Id, Role = "Admin" }));

      public IQueryable<PrincipalClaim<Guid>> Claims => _stored.Claims;
  }

  services.AddScoped<IPrincipalDirectory<Guid>, AppPrincipalDirectory>();   // kept: the default is a TryAdd
  ```

  Pin the agreement with a test that builds a principal the way the host does and compares its roles and claims with
  the directory. The forward filter stays the authority: a principal the inverse lists is still checked when it reads
  the record.
</Callout>

For shares alone, `IResourceGrantStore.GetGrantsAsync(resourceType, resourceId)` still lists the users and roles a
record is shared with.
