---
title: Reacting to deletions
description: Publish EntitiesDeleted<TEntity> for marked entities — cascades included — so the module that owns soft-referencing data cleans it up in the same unit of work.
---

Data that belongs to records of many kinds — notes, files, comments, a per-recipient inbox — points at its owner by
an id without a foreign key: a **soft reference**. Nothing in the database removes it when the owner goes, and having
every delete handler remove it by hand couples each deleting module to every module that keeps such data. Entity
lifecycle events invert that: the owner entity is marked once, and the module that owns the referencing data reacts.

## Mark the owner, consume the event

```csharp
using Elarion.Abstractions.Messaging;

[PublishLifecycleEvents]
public sealed class Property {
    public Guid Id { get; init; }
    // ...
}
```

```csharp
// In the Notes module — the Properties module knows nothing about notes.
[Service]
public sealed class NoteCleanup(AppDbContext db) {
    [ConsumeEvent]
    public async ValueTask OnPropertiesDeleted(EntitiesDeleted<Property> deleted, CancellationToken ct) {
        var notes = await db.Notes.Where(n => n.OwnerKind == RecordKind.Property && deleted.Ids.Contains(n.OwnerId))
            .ToListAsync(ct);
        db.Notes.RemoveRange(notes);   // saved by the same SaveChanges that deletes the property
    }
}
```

```csharp
// Program.cs (or the persistence assembly's registration)
builder.Services.AddElarionEntityLifecycleEvents<AppDbContext>();
```

When a save deletes rows of a marked entity, the interceptor publishes an `EntitiesDeleted<TEntity>` per entity
type with the deleted ids, on the inline [domain-event plane](/docs/capabilities/events): before the `DELETE`
runs, in the same scope. A consumer can still read the rows, its changes are saved by the same `SaveChanges`, and a
consumer failure fails the save — nothing is deleted. Each id is published once per save; a later round (rows a
consumer deleted) can publish a second event of the same type for the new ids.

**Delete inside a transaction** — a command, whose pipeline opens one, or a transaction you open. Then the cascade
query, the consumers and the `DELETE` share it. Without one, the queries and consumers run before EF Core opens the
save's own transaction, and a consumer that saves is refused (below).

### A consumer that saves

A consumer may save the context, typically by running the owning module's delete command through `IHandlerSender`.
That nested save continues the same publication: what was already published is not published again, so the recursion
ends. It writes the outer deletion early, which is safe only inside a transaction (inside a command it becomes a
savepoint of the command's transaction); outside one it is refused rather than committing a deletion before the
remaining consumers ran. A consumer that only changes the context, and leaves saving to the outer `SaveChanges`, works
anywhere.

## What counts as deleted

- **Tracked deletions** — `Remove`, a deletion made through a navigation, or an orphan or cascade EF Core would
  delete only at save time (`CascadeDeleteTiming`/`DeleteOrphansTiming.OnSaveChanges`), which is applied first.
- **Database cascades.** Deleting a row whose cascading foreign keys reach a marked entity (a ledger takes its
  accounts) deletes rows the change tracker never loaded. The interceptor follows the model's cascading foreign keys
  and queries those rows' ids before the `DELETE`, so they are published too. A dependent the same save moves to
  another principal (`account.LedgerId = mergedInto` before removing the old ledger) survives the cascade and is not
  reported.
- **Deletions made by consumers.** A consumer that removes rows of another marked entity triggers another round, to
  a fixed point: a removed note's files are cleaned up by the files module's own consumer.

Two paths would bypass the event and are refused: `ExecuteDelete`/`ExecuteDeleteAsync` that deletes rows of a
marked entity, or of one whose deletion cascades to it, throws at query compilation, whatever the query joins (load
the rows, `Remove` them, save); and the synchronous `SaveChanges` throws while such a deletion is pending, because it
cannot await the consumers. Raw SQL `DELETE` is outside the guard. So are Elarion's own purge jobs, which delete with
`ExecuteDelete`: do not add a cascading foreign key from a framework table to a marked entity, or those jobs start
failing.

### What it does not guarantee

- **Concurrent inserts.** A soft reference has no foreign key, so a note added for a property while that property is
  being deleted, by a transaction the cleanup query does not see, survives as an orphan. The same holds for a
  cascading dependent inserted after the cascade query ran. Where that matters, lock the owner row in both the delete
  and the insert (`LockRowAsync`, see [Coordination](/docs/capabilities/coordination#row-and-advisory-locks)).
- **Retrying a save by hand.** A `SaveChangesAsync` called again on the same context after a failure runs the
  consumers again on a change tracker that still holds their earlier changes; write consumers so that a second run is
  harmless, or retry with a fresh scope. EF Core's own execution-strategy retries happen below the interceptor and do
  not re-run consumers.

## Requirements

- The marked entity, and every entity on a cascade path to it, has a single `Guid` primary key (the Elarion
  convention); the interceptor names the entity otherwise.
- The context is resolved from a DI scope with `AddDbContext` (scoped options, the default): the consumers change
  that scope's context. A context from `AddDbContextFactory`, `AddDbContextPool` or singleton options is refused when
  it saves such a deletion, instead of silently saving without the consumers' cleanup.
- No inheritance: a marked entity, and every entity on a cascade path to it, is not part of a hierarchy (TPH, TPT or
  TPC). The interceptor names the entity otherwise.
- Cascades follow primary keys; a cascading foreign key to an alternate key on the path is refused. Only database
  cascades (`DeleteBehavior.Cascade`) are queried — a `ClientCascade` reaches tracked rows only, which the change
  tracker reports itself.

## Interceptor order

The consumers change the change tracker inside the save, so anything that must see their changes runs **after** the
lifecycle interceptor. Register `AddElarionEntityLifecycleEvents<TDbContext>()` before tenant scoping (which stamps
the rows consumers add) and auditing (which records the rows they remove); building a context with either already
attached throws. A soft-delete interceptor, by contrast, belongs before it, so a soft deletion is an update by the time
lifecycle events look — see
[EF Core › Interceptors and their order](/docs/capabilities/entity-framework#interceptors-and-their-order).

## Why only deletions

There is no `EntitiesAdded<T>` or `EntitiesUpdated<T>`, on purpose. Deletion needs the framework for two reasons
that inserts and updates do not share:

- **It breaks data it does not own.** Notes and files keep pointing at a deleted record, and the deleting module
  cannot know which modules keep such data. Inserting or updating the record leaves every reference valid.
- **Part of it is invisible to your code.** A database cascade deletes rows no handler loaded; only an interceptor
  that reads the EF model finds them before the `DELETE`. An insert or update is always written by code that knows
  what it wrote.

A framework event for inserts and updates would also be the wrong tool:

- **It carries no intent.** "Contact updated" does not say whether the contact was renamed, reassigned, or stamped by
  a background worker, so consumers would diff columns of another module's table.
- **It could not be complete.** Leased work, the outbox and bulk paths rely on `ExecuteUpdate`, so the event could
  not refuse it the way deletion refuses `ExecuteDelete`.
- **It would be expensive.** It would run a consumer in every save.

Use the tool that fits the need:

| You need | Use |
| --- | --- |
| Another module reacts to a business change | an intent-named event the handler publishes — inline [domain event](/docs/capabilities/events) or after-commit integration event |
| Field-level history | [`[Auditable]`](/docs/concepts/auditing) with EF change capture |
| Cache freshness | [`[CacheInvalidate]`](/docs/capabilities/caching) |
| A browser shows the change, such as a live dashboard over several tables | a [client event](/docs/capabilities/events/client-events): a re-query hint after commit |
| A search index or stored projection | an integration event, consumed after commit |

## An inbox fed by domain events

The same shape serves a per-recipient inbox (mentions, rescheduled appointments): producers publish their own domain
events (`NoteMentionedUser`, `AppointmentRescheduled`), and the notifications module consumes them and writes the inbox
rows in the producer's transaction. The producers depend on their own event types, never on the inbox's contract, and
the notifications module can be disabled without touching them.
