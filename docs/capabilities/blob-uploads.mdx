---
title: Blob uploads
description: Pre-upload files over an open, resumable transport (tus) or a minimal direct endpoint, reference them when creating an entity, and reclaim abandoned uploads automatically with a pending/commit/TTL lifecycle.
---

A common requirement is to **create an entity (say a `Contract`) and attach files to it**. Over a JSON
transport (JSON-RPC) the entity and its files cannot travel together — JSON cannot carry binary. So the
file is uploaded *separately*, the upload returns a reference, and the entity-creation call carries that
reference. This is the same shape S3 apps use: **pre-upload, then reference**.

The hard part is the orphan: if the user uploads a file but never finishes creating the entity (they
cancel, or the browser closes), there is **no backend signal**. Elarion answers this the way S3
lifecycle rules do — with **time plus an explicit promote**:

<Steps>
<Step>**Upload** produces a `Pending` blob with a time-to-live.</Step>
<Step>**Commit** promotes it to `Committed` inside the same transaction that creates the referencing entity — atomic with the entity insert.</Step>
<Step>**Garbage collection** deletes any `Pending` blob whose TTL elapses without a commit.</Step>
</Steps>

A referenced upload is kept forever; an abandoned one is reclaimed. The TTL *is* the missing signal.
This builds directly on [blob storage](/docs/capabilities/blob-storage) and stays S3-free — the upload
protocol lives only at the HTTP layer.

## The lifecycle

The lifecycle is a small capability over `IBlobStore`, provider-neutral and S3-free. `BlobUploadRequest`
gains `InitialState` (defaults to `Committed`, so a plain `SaveAsync` stays permanent) and `ExpiresAt`;
upload transports save with `InitialState = Pending` and an `ExpiresAt`. `IBlobLifecycle` adds two
operations:

| Method | Purpose |
| --- | --- |
| `CommitAsync(blobRef, ct)` | Promotes a `Pending` blob to `Committed` and clears its expiry. Idempotent; participates in the **caller's** transaction (it mutates within the ambient transaction and persists on the caller's `SaveChangesAsync`), so the commit and the entity insert are atomic. Returns `false` when the blob no longer exists. |
| `DeleteExpiredPendingAsync(olderThanUtc, batchSize, ct)` | The garbage-collection entry point. |

A `Pending` blob has two fates. Either an application **commits** it — the pre-upload-then-reference pattern
[below](#attaching-a-file-to-an-entity), which keeps it forever — or it is **discarded**: a consumed temp
file is deleted explicitly (`IBlobStore.DeleteAsync`) and anything left over is reclaimed by the collector
after its TTL (see [temp-file flows](#streaming-downloads-and-temp-file-flows)). A blob is never both.

Register the PostgreSQL lifecycle and its background collector:

```csharp
services.AddElarionPostgreSqlBlobLifecycle<AppDbContext>(); // store + lifecycle + GC sweeper
// (streaming reads clone the context's connection — no other wiring, ADR-0041)
// in OnModelCreating:
modelBuilder.UseElarionBlobStorage();
```

This adds `state` and `expires_at` columns plus a partial index over pending rows; create a migration
(or `EnsureCreated` for throwaway databases) as for any model change.

### Attaching a file to an entity

The command carries the upload as an [`UploadedFile`](#passing-an-upload-to-a-handler), and the handler keeps it
through `IUploadedFiles`, which commits only the caller's own pending upload:

```csharp
[Handler]
[ProducesError(ErrorCodes.UploadNotFound, ErrorKind.Validation)]
[ProducesError(ErrorCodes.UploadContentType, ErrorKind.Validation)]
public sealed class CreateContract(AppDbContext db, IUploadedFiles uploads)
    : IHandler<CreateContract.Command, Result<CreateContractResponse>> {
    public sealed record Command : ICommand {
        public required string Title { get; init; }
        public required UploadedFile Attachment { get; init; }   // the id the upload endpoint answered
    }

    public async ValueTask<Result<CreateContractResponse>> HandleAsync(Command command, CancellationToken ct) {
        // Promote the pre-uploaded blob in the same transaction as the entity insert.
        var kept = await uploads.CommitAsync(
            command.Attachment, new UploadConstraints { ContentTypes = ["application/pdf"] }, ct);
        if (!kept.IsSuccess) return kept.Error;

        var contract = new Contract {
            Title = command.Title,
            AttachmentBlobId = kept.Value.BlobId,       // read it later through IBlobStore
            AttachmentName = kept.Value.FileName,
        };
        db.Contracts.Add(contract);
        await db.SaveChangesAsync(ct); // commit + insert are atomic
        return new CreateContractResponse(contract.Id);
    }
}
```

If the handler rolls back, the blob stays `Pending` and the collector reclaims it after
`Ttl + SafetyMargin`. The collector deletes only rows still pending, so a commit that lands first wins
the race and a never-committed upload is always reclaimed.

<Callout type="info">
The blob store is registered against your `DbContext` as a scoped service, so `CommitAsync` shares the
same `DbContext` and transaction as your handler — no extra wiring. Wrap the handler in a transaction
decorator (or rely on `SaveChangesAsync`'s implicit transaction) so the promote and the insert commit
together.
</Callout>

## Upload transports

The lifecycle is transport-neutral. Two open transports produce `Pending` blobs over it; both stay
S3-free. Pick by client needs.

### tus — the resumable standard

[tus 1.0](https://tus.io) is the open, resumable upload protocol built by the Uppy authors and the
basis of the IETF *Resumable Uploads* draft. It is **resumable, handles large files, and survives a
browser close mid-upload**, and is supported natively by Uppy (`@uppy/tus`) and `tus-js-client`. This is
the recommended transport for new frontends.

```csharp
services.AddElarionResumableBlobUploads();              // in-memory staging by default
app.MapElarionResumableBlobUploads().RequireAuthorization();
```

`MapElarionResumableBlobUploads` implements Creation, Core, Expiration, and Termination: `OPTIONS` advertises
capabilities, `POST` creates an upload (baking the current user's id), `PATCH`/`HEAD` stream and resume,
`DELETE` aborts. When an upload completes, the staged bytes are written as a `Pending` blob and its
reference is returned in the `Elarion-Blob-Ref` response header (also available on `HEAD`) — the handle
the client passes to entity creation.

Under the endpoints sits the protocol-neutral **`IStagedUploadStore`** seam: offset-guarded appends, an
explicit idempotent completion (so a crash between the last chunk and completion self-heals on the next
status probe), and deferred-length sessions — the shape of the IETF *Resumable Uploads* draft ("tus 2.0"),
which will be a second adapter over the same seam. All policy (upload expiry, pending-blob TTL, completed-
session retention) lives in `ResumableBlobUploadOptions` and reaches the store as data, so staging backends are
protocol-free and interchangeable.

<Callout type="info">
The default in-memory staging keeps in-progress uploads in process. For resumability **across restarts
and instances**, add the durable PostgreSQL staging store — it persists staged bytes and reaps both
incomplete sessions (the analog of S3's *abort incomplete multipart upload*) and completed sessions once
past a retention window:

```csharp
services.AddElarionResumableBlobUploads();
services.AddElarionPostgreSqlStagedUploads<AppDbContext>();
modelBuilder.UseElarionBlobStorage();  // blob tables, in OnModelCreating
modelBuilder.UseElarionStagedUploads(); // staging table, in OnModelCreating
```

`AddElarionPostgreSqlStagedUploads` also wires the PostgreSQL **blob lifecycle** and its
`BlobGarbageCollector` (idempotently, via `AddElarionPostgreSqlBlobLifecycle`) — a completed upload
produces a *pending* blob, so without that collector an abandoned upload would leak its blob forever. Map
the blob tables with `UseElarionBlobStorage()` alongside the staging table. Both wiring methods take
optional `tableName` (plus `contentTableName` on the blob side) and `schema` parameters and a `snakeCase`
toggle (default `true`; `false` switches to PascalCase names — `StagedUploads`,
`StoredBlobs`/`BlobContents`); the stores' raw Npgsql SQL (content streaming and the staging conditional
append) is built from the EF model, so the overrides apply there too. On a `[GenerateDbSets]` context,
`[GenerateElarionBlobStorage]` and `[GenerateElarionStagedUploads]` (each with optional
`SnakeCase`/`TableName`/`Schema` — the blob attribute also takes `ContentTableName`) replace the
hand-written calls: the bundled generators emit the `DbSet`s and apply the same configuration through the
EF generator's model-config seam (`ELBLB001`/`ELBLB002` if `[GenerateDbSets]` is missing). A completed
session row is retained for `ResumableBlobUploadOptions.CompletedSessionRetention` (default 1 hour) so a client `HEAD`
can still fetch the reference, then reclaimed; the session collector applies a
`StagedUploadGcOptions.SafetyMargin` (default 1 minute) to the expiry cutoff, mirroring the blob
collector.

Prefer Azure Blob Storage? `AddElarionAzureStagedUploads(connectionString)` stages each session as an
**append blob** — the offset guard is Azure's server-side `If-Append-Position-Equal` precondition, and
completion is a server-side copy into the final pending blob, so bytes never round-trip through the
application. The matching `AzureBlobStore` serves reads and the commit lifecycle over blob metadata
(commit takes effect immediately rather than joining a caller transaction — the documented delta from the
PostgreSQL tier).
</Callout>

Cross-origin frontends must expose the reference header via CORS:
`Access-Control-Expose-Headers: Upload-Offset, Location, Upload-Expires, Elarion-Blob-Ref`. Behind a
reverse proxy, enable `UseForwardedHeaders` so the `Location` header reflects the public scheme and host
rather than the internal one.

### Direct upload — minimal endpoint

For FilePond's `process`/`revert` and plain `fetch`/`<form>` clients, a single "accept bytes, return a
reference" endpoint is the smallest path. It is not a new protocol.

```csharp
services.AddElarionBlobUploads(o => o.MaxContentLength = 25 * 1024 * 1024);
app.MapElarionBlobUploads().RequireAuthorization();
```

`POST` (multipart or raw body) writes a `Pending` blob and returns its id as `text/plain`; `DELETE /{id}`
cancels an owner's pending upload (a committed blob answers `404`: it belongs to the record that kept it). Both enforce authentication, the configured size cap, and an optional
content-type allow-list. Ownership is recorded as a dedicated `BlobUploadRequest.OwnerId` (surfaced as
`BlobMetadata.OwnerId`) and compared **exactly** on cancel — not parsed from the stored name — so an id
containing the naming separator cannot be forged, and a blob with no recorded owner is denied to everyone.
The tus transport applies the same owner-exact, fail-closed check to its `HEAD`/`PATCH`/`DELETE`.

`AddElarionBlobUploads` and `AddElarionResumableBlobUploads` register their options through the options pattern, so
a later `services.Configure<BlobUploadEndpointOptions>(…)` reaches the endpoints too, and code that needs the
configured values — the route prefix, the container — reads `IOptions<BlobUploadEndpointOptions>` (or
`IOptions<ResumableBlobUploadOptions>`) and gets exactly what the endpoints use. Every response of the direct upload,
cancel and download endpoints carries `X-Content-Type-Options: nosniff`.

<Callout type="warn">
Both transports bake the current user's id into the upload, so the host must register an `ICurrentUser`
(via `AddElarionCurrentUser` or the optional Identity integration) and opt the route group into
`.RequireAuthorization(...)`. Per-endpoint authorization is the host's job, as for all generated routes.
</Callout>

### Client adapters

- **Uppy** — `@uppy/tus` against `MapElarionResumableBlobUploads` (recommended), or `@uppy/aws-s3`'s
  `getUploadParameters` / `@uppy/xhr-upload` against the direct endpoint.
- **FilePond** — `server.process` → `POST` the direct endpoint (the response body is the file id);
  `server.revert` → `DELETE /{id}`. FilePond's chunked mode is tus-derived but not identical, so its
  resumable path needs a small client adapter.

## Passing an upload to a handler

A handler takes an upload as an **`UploadedFile`** member: on every JSON surface (JSON-RPC, MCP, HTTP bodies) a plain
string, the blob id the upload endpoint answered with. It reads, keeps or discards the file only through
**`IUploadedFiles`**, never by handing that id to `IBlobStore` itself:

```csharp
services.AddElarionPostgreSqlBlobLifecycle<AppDbContext>();
services.AddElarionBlobUploads(o => o.Ttl = TimeSpan.FromHours(2));   // and/or AddElarionResumableBlobUploads
services.AddElarionUploadedFiles();                                   // IUploadedFiles

app.MapElarionBlobUploads().RequireAuthorization();
```

```csharp
[Handler]   // [UploadLimits] puts upload.not_found and the code of each declared limit into the error contract
public sealed class AnalyzeStatement(IUploadedFiles uploads, StatementParser parser)
    : IHandler<AnalyzeStatement.Command, Result<StatementAnalysis>> {
    public sealed record Command : ICommand {
        [UploadLimits(MaxBytes = 50L * 1024 * 1024, ContentTypes = ["text/csv", "application/xml"])]
        public required UploadedFile Statement { get; init; }
    }

    public async ValueTask<Result<StatementAnalysis>> HandleAsync(Command command, CancellationToken ct) {
        var opened = await uploads.OpenAsync(command.Statement, cancellationToken: ct);   // the declared limits apply
        if (!opened.IsSuccess) return opened.Error;

        await using var file = opened.Value;   // Content, ContentType, FileName, Length, ContentSha256
        return await parser.AnalyzeAsync(file.Content, ct);
    }
}
```

`IUploadedFiles` has three operations:

| Method | Does |
| --- | --- |
| `OpenAsync(file, constraints?, ct)` | Opens the content for reading. The upload stays pending, so the next step of a flow opens it again. Dispose the result. |
| `CommitAsync(file, constraints?, ct)` | Keeps it: promotes the pending blob inside the caller's transaction ([above](#attaching-a-file-to-an-entity)) and answers a `CommittedUpload` (`BlobId`, `FileName`, `ContentType`, `Length`, `ContentSha256`) for the record. Needs an `IBlobLifecycle`. |
| `DeleteAsync(file, ct)` | Discards it now instead of after its TTL. Idempotent; `false` when there was nothing of the caller's to delete. On the PostgreSQL store it saves the `DbContext` it shares with the handler: call it after the handler's own save ([below](#streaming-downloads-and-temp-file-flows)). |

Every operation answers only an upload that is **still pending**, whose recorded owner is **exactly the current
user**, and that lies in an **upload container** (`UploadedFilesOptions.Containers`, default `uploads`, the container
of both endpoints; list a renamed endpoint container there). A missing, expired, already kept, someone else's,
unowned or foreign-container blob, and any call by an anonymous caller, all answer the same error, so a caller cannot
tell which ids exist. A kept blob belongs to its record from then on: the record's own authorization guards it, and the
reference no longer opens it.

| Code | When | `data` |
| --- | --- | --- |
| `upload.not_found` | No pending upload of the caller has that id. The caller uploads again. | none |
| `upload.too_large` | The file is larger than `UploadConstraints.MaxBytes`. | `UploadTooLargeData`: `maxBytes`, the file's `length` |
| `upload.content_type` | The declared content type is not in `UploadConstraints.ContentTypes` (exact, case-insensitive, parameters such as `; charset` ignored). | `UploadContentTypeData`: the accepted `contentTypes`, the file's `contentType` |
| `upload.file_extension` | The stored file name does not end in one of `UploadConstraints.FileExtensions` (case-insensitive; a file uploaded without a name is stored as `upload`). | `UploadFileExtensionData`: the accepted `fileExtensions`, the file's `fileName` |

The limits are checked in that order, and the first one the file breaks answers. All four are `Validation` errors
(JSON-RPC `-32602`, HTTP `400`) the handler returns. A request that
[declares its limits](#declaring-the-limits-on-the-member) has `upload.not_found` and the code of each declared limit,
with its payload, in its error contract already. A handler that only passes `UploadConstraints` declares the codes it
can produce with their payload:

```csharp
[ProducesError(ErrorCodes.UploadNotFound, ErrorKind.Validation)]
[ProducesError(ErrorCodes.UploadTooLarge, ErrorKind.Validation, typeof(UploadTooLargeData))]
```

A declaration of an upload code with another payload, or none, is the warning `ELERR004`: it would hide the typed data
from the schema and the client.

The `message` is an English fallback with the limit in bytes. To say it in the user's language, branch on the code and
word the payload: the [generated client](/docs/capabilities/transports/typescript-client#uploaded-files) types `data`
per code, and its own check before the upload reports the same codes and data.

```ts
catch (error) {
  if (isRpcMethodError('statements.analyze', error) && error.code === 'upload.too_large')
    showError(t('upload.tooLarge', { max: formatBytes(error.data.maxBytes) }))
}
```

The limits are the handler's per operation; the endpoints' `MaxContentLength`/`MaxSize` and `AllowedContentTypes`
still cap what can be uploaded at all. The content type and the file name are the ones the client declared, not
sniffed: treat the content as untrusted input.

An upload lives until it is committed, deleted, or collected after the endpoint's `Ttl` (`BlobUploadEndpointOptions.Ttl`,
`ResumableBlobUploadOptions.Ttl`, default 30 minutes). A multi-step flow (analyze, preview, commit) passes the same
`UploadedFile` to every step, so raise the `Ttl` to the longest time a user may spend in it.

### Declaring the limits on the member

`[UploadLimits(MaxBytes = …, ContentTypes = […], FileExtensions = […])]` on the request member declares the limits
once, where every side reads them. Before the handler runs, the pipeline declares them for the request's files to the
scoped `IDeclaredUploadConstraints` (the same `AddElarionUploadedFiles` registration), and every `OpenAsync` and
`CommitAsync` of those files checks them — the handler passes no constraints and declares no upload error. The schema
exports them next to the marker, and the generated client rejects a file that breaks them before uploading it.

```csharp
public sealed record Command : ICommand {
    [UploadLimits(MaxBytes = 50L * 1024 * 1024, ContentTypes = ["text/csv", "application/xml"])]
    public required UploadedFile Statement { get; init; }

    // On a collection the limits apply to every file; [MaxLength] bounds how many there are.
    [MaxLength(10), UploadLimits(MaxBytes = 5L * 1024 * 1024, ContentTypes = ["application/pdf"])]
    public IReadOnlyList<UploadedFile> Receipts { get; init; } = [];

    // Browsers declare a spreadsheet's type differently per system, often as application/octet-stream.
    [UploadLimits(MaxBytes = 10L * 1024 * 1024, FileExtensions = [".xlsx", ".xls"])]
    public UploadedFile? Workbook { get; init; }
}
```

| Rule | |
| --- | --- |
| Members | `UploadedFile`, `UploadedFile?`, or a collection of them (array, list, read-only collection), on the handler's request type, its own or inherited. On a positional record, target the property (`[property: UploadLimits(…)]`) or the parameter. |
| Limits | `MaxBytes` (`0` = none), `ContentTypes` (empty = any) and `FileExtensions` (empty = any), compared as `UploadConstraints` compares them. At least one; every one declared must hold. |
| Types or extensions | The content type is what the browser declared, and for `.xlsx`, `.vcf` or `.ics` that varies between systems or is missing (sent as `application/octet-stream`). Accept such formats by `FileExtensions` (each with its leading dot, compared case-insensitively against the end of the stored file name), not `ContentTypes`; declaring both requires both. |
| Error contract | `upload.not_found`, and `upload.too_large`, `upload.content_type` or `upload.file_extension` for each kind of limit the request declares, with its payload — the handler declares none of them. |
| Several | Constraints a call still passes to `IUploadedFiles` apply too; a file declared by two members must satisfy both. Declarations only tighten. |
| Build errors | `ELUPL001` for a member that holds no uploaded file, an extension that is not a dot followed by a name (`"xlsx"`, `".x ls"`), or a declaration without a valid limit; `ELUPL002` for a member of a type that is not a handler's request in the assembly — a declaration the pipeline would not enforce is never accepted. |
| Fail closed | A handler with declared limits needs an `IDeclaredUploadConstraints` (registered by `AddElarionUploadedFiles`); without one its pipeline does not build. A singleton handler cannot declare limits (`ELSG013`). |

The exported schema marks the member `x-elarion-upload` (a string), with the declared limits as
`x-elarion-max-bytes`, `x-elarion-content-types` and `x-elarion-file-extensions` (on the items of a collection), and the
[generated TypeScript client](/docs/capabilities/transports/typescript-client#uploaded-files) takes a `File` there,
checks it against those limits and uploads it before the call; `rpc.$uploadFile(file, { method, member })` uploads once
for a multi-step flow after the same check, and `rpcLimits` shows the limits to the user (an `<input accept>` from
`fileExtensions`). An MCP tool caller passes the id. The
[OpenAPI document](/docs/capabilities/transports/openapi) carries the same marker and limits. See
[ADR-0105](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0105-uploaded-files-are-handler-parameters.md)
and [ADR-0100](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0100-the-schema-exports-constants-presets-and-limits.md).

## Streaming downloads and temp-file flows

The staging area is also the framework's answer for **large files in handler flows** — the tier above the
in-memory [`ElarionFile` payload](/docs/capabilities/transports/http-endpoints#files-downloads-and-uploads)
(which buffers and is the right default only up to a few megabytes). Handlers never carry big payloads;
they carry **pointers into the staging area**, and the pending state doubles as temp-file semantics: what
is never committed is garbage-collected after its TTL.

The read side is the owner-scoped streaming download endpoint:

```csharp
app.MapElarionBlobDownloads().RequireAuthorization();   // GET {prefix}/{blobId}; requires AddElarionBlobUploads
```

`GET /{blobId}` streams the blob with its content type and leaf file name (`Content-Disposition:
attachment`), applying the same exact-owner, fail-closed check as cancel — a missing, foreign-container,
unowned, committed, or someone else's blob is `404`, so ownership is never leaked. Once a handler commits a blob to
a record, the record's own (authorized) download path serves it; the uploader cannot keep reading it here after
losing access to the record.

**Import (large upload → processing handler):**

1. The client uploads via tus (or the direct endpoint) into the staging area → gets a pending blob reference.
2. It calls the processing handler (any transport) with that reference as an
   [`UploadedFile`](#passing-an-upload-to-a-handler) member.
3. The handler streams it from `IUploadedFiles.OpenAsync(...)`, processes it, and disposes of the temp file.

A consumed import is the mirror image of [attaching a file to an entity](#attaching-a-file-to-an-entity):
you never keep it, so **do not `CommitAsync` it** — commit means "promote to permanent and clear the
expiry," the opposite of what a throwaway import wants. There are two ways to reclaim it:

- **Explicitly — delete it the moment you are done**, so a large temp file is not left occupying storage
  for the whole TTL:

```csharp
public async ValueTask<Result<Unit>> HandleAsync(ImportRows.Command command, CancellationToken ct) {
    var opened = await uploads.OpenAsync(command.File, new UploadConstraints { ContentTypes = ["text/csv"] }, ct);
    if (!opened.IsSuccess) {
        return opened.Error;                            // upload.not_found: expired, consumed or not the caller's
    }

    await using (var file = opened.Value) {
        await importer.IngestAsync(file.Content, ct);   // stream and process
    }

    await db.SaveChangesAsync(ct);                      // the handler's own save first (see below)
    await uploads.DeleteAsync(command.File, ct);        // reclaim now — no waiting for the GC
    return Unit.Value;
}
```

- **Implicitly — do nothing**, and the [blob garbage collector](#the-lifecycle) reclaims the pending blob
  once its `ExpiresAt` passes. This is also the safety net if the process crashes before the explicit delete.

<Callout type="info">
Whether that delete is transactional depends on the backend. On a **same-database store (PostgreSQL)** it
joins the caller's unit of work: inside a command's transaction the reclaim commits atomically with the
imported rows and **rolls back with them** if the import fails, leaving the file in place to retry — so
calling `DeleteAsync` inside the handler is safe. On an **external store (Azure Blob Storage)** the delete is
an immediate side effect, not part of your database transaction, so delete only **after** the import
transaction commits — or skip the explicit delete and let the garbage collector reclaim it.
</Callout>

<Callout type="warn">
On the PostgreSQL store, `DeleteAsync` removes the blob row through the scoped `DbContext` it shares with the handler
and calls `SaveChangesAsync` on it. That save writes **everything the handler still tracks** at that moment, not only
the delete. Call `DeleteAsync` **after** the handler's own `SaveChangesAsync`, as the example does, never between
changing tracked entities and saving them: a delete in between would save half-made changes before the handler
validated or finished them.
</Callout>

Note the handler works with the **pending blob** the upload produced, never the staging *session*: by the
time it runs, the resumable upload has already been sealed into that blob (the session is cleaned up
separately by the staged-upload collector, and must outlive the client's completion probe). "Removing it
from staging" therefore means deleting the pending blob, exactly as above.

**Export (handler-produced artifact → streaming download):**

```csharp
public async ValueTask<Result<ExportPointer>> HandleAsync(Command command, CancellationToken ct) {
    await using var artifact = await _exporter.BuildAsync(command.List, ct);   // a stream, never buffered
    var blobRef = await _blobs.SaveAsync(new BlobUploadRequest {
        Container = "uploads",                       // the download endpoint's configured container
        Name = $"{_currentUser.UserId}/{Guid.CreateVersion7():N}/{command.List}.xlsx",
        ContentType = "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        InitialState = BlobLifecycleState.Pending,   // temp: GC reclaims it if never downloaded/committed
        ExpiresAt = _timeProvider.GetUtcNow() + TimeSpan.FromMinutes(30),
        OwnerId = _currentUser.UserId,               // only the requesting user may download it
    }, artifact, ct);

    return new ExportPointer(blobRef.Value);         // the client GETs {prefix}/{id} to stream it
}
```

The response DTO carries only the blob id — small, cacheable, schema-friendly — and the actual bytes move
once, streamed, over the download endpoint.

### Streaming a ZIP archive into the response body

"Download all of these as one file" is the one export shape the single-blob download endpoint cannot
serve: the archive is assembled per request from several stored blobs and never exists as a blob of its
own. An HTTP-only handler builds it while it is sent: an `[HttpEndpoint]` without `[Handler]` returns a
[streamed file](/docs/capabilities/transports/http-endpoints#streamed-files-http-only-endpoints) whose writer gets the
response body, so nothing is buffered in memory or staged in the database, and authorization and the module's
feature gate guard it like every handler:

```csharp
[HttpEndpoint("exports/{id}/bundle")]
[RequirePermission("exports", "read")]
public sealed class DownloadBundle(IExportParts parts, IBlobStore blobs, ILogger<DownloadBundle> logger)
    : IHandler<DownloadBundle.Query, Result<ElarionStreamedFile>> {
    public sealed record Query : IQuery {
        public required Guid Id { get; init; }
    }

    public async ValueTask<Result<ElarionStreamedFile>> HandleAsync(Query query, CancellationToken ct) {
        var members = await parts.ListAsync(query.Id, ct);
        if (members.Count == 0) return AppError.NotFound("Nothing to bundle.");

        return ElarionStreamedFile.FromWriter(async (body, ct) => {
            await using var archive = await ZipArchive.CreateAsync(
                body, ZipArchiveMode.Create, leaveOpen: true, entryNameEncoding: null, ct);
            foreach (var member in members) {
                await using var download = await blobs.OpenReadAsync(new BlobRef { Value = member.BlobId }, ct);
                if (download is null) {
                    // Expired or reclaimed: leave it out, but say so — a listing may name it.
                    logger.LogWarning("Bundle member {BlobId} has vanished.", member.BlobId);
                    continue;
                }

                var entry = archive.CreateEntry(member.FileName, CompressionLevel.Fastest);
                await using var entryStream = await entry.OpenAsync(ct);
                await download.Content.CopyToAsync(entryStream, ct);
            }
        }, "application/zip") with { FileName = $"bundle-{query.Id}.zip" };
    }
}
```

Two things the framework takes care of here:

- **The synchronous trailer write.** `System.IO.Compression` has async APIs (`ZipArchive.CreateAsync`,
  `ZipArchiveEntry.OpenAsync`, `ZipArchive.DisposeAsync`), but the entry stream from `OpenAsync` does not override
  `DisposeAsync`: `await using` falls through to the synchronous `Dispose()`, which writes the entry's compressed
  trailer and data descriptor synchronously, even with `CompressionLevel.NoCompression`. Kestrel and `TestServer`
  refuse synchronous body writes (`AllowSynchronousIO` is `false`), and by then the `200` and its headers are sent,
  so a host route would hang with a download that never finishes. The body a streamed file's writer receives holds
  those few synchronous bytes and sends them with the next asynchronous write, so the handler needs no
  `AllowSynchronousIO`. The member bytes still copy asynchronously and unbuffered. This is a BCL gap, worth an
  upstream fix in `dotnet/runtime` (the entry stream should write its trailer in `DisposeAsync`).
- **A mid-stream failure aborts.** Once the status line is sent, an exception in the writer aborts the connection, the
  only honest signal: the client sees a failed download, not a truncated archive with a valid-looking central
  directory.

A route you map yourself outside the handler tier needs the same care: scope
`IHttpBodyControlFeature.AllowSynchronousIO = true` to that one response (never `KestrelServerOptions` globally, which
gives every endpoint a thread-blocking write path), and call `HttpContext.Abort()` on a failure after the headers.

## Not S3 on the wire

Elarion deliberately does **not** implement the S3 wire protocol (SigV4, `aws-chunked` streaming
signatures, multipart XML). That is the interop-fragile, expensive part of S3, and upload widgets never
need it — Uppy treats every upload URL as opaque. The S3 wire protocol is only required for real AWS SDK
/ CLI interoperability, which is a non-goal. The abstraction stays S3-free — `Elarion.Blobs.Azure` is
exactly such a direct-to-storage backend behind the neutral seams, and a presigned-URL capability could
be added the same way without changing the lifecycle.
