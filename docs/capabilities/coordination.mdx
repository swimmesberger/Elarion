title: Coordination & role leases
description: Elect one instance for a coarse application role on PostgreSQL, gate work at the holder, and route HTTP traffic to it when needed — and claim rows of your own queue tables with leased work rows.
---

Elarion has four deliberately different coordination shapes. Choose the one that matches the unit
being coordinated:

| Need | Primitive | Coordination key |
| --- | --- | --- |
| Run one recurring occurrence across the cluster | [Scheduler claim](/docs/capabilities/scheduling/multi-node) | Job + due time |
| Deliver one integration consumer invocation at a time | [Outbox delivery lease](/docs/capabilities/events/backends) | Message + consumer |
| Work through your own queue table, one worker per row | [Leased work rows](#leased-work-rows) | Row id + lease token |
| Serialize writers of one row or key inside a transaction | [Row and advisory locks](#row-and-advisory-locks) | Entity key, or scope + key |
| Make exactly one instance hold a long-lived application role | **Role lease** | Role name |

A role lease answers a coarse question such as “which instance is the maintenance coordinator?” It
is a heartbeat-renewed row in the application's PostgreSQL database, exposed as an `IRoleLease`
keyed by role name. The current holder renews; other instances keep trying; graceful shutdown
releases immediately; a crashed holder fails over when its lease expires.

<Callout type="warn">
  A role lease is **not a distributed-lock API**. Do not create one per tenant, record, or work item.
  An application should have a handful of stable roles. Use database constraints and optimistic
  concurrency for rows, scheduler claims for job occurrences, outbox leases for messages, and
  leased work rows for your own queue tables.
</Callout>

This default targets Elarion's normal scale: roughly 1–10 application nodes on the PostgreSQL the app
already runs. Beyond that tier, replace the coordination seam with dedicated infrastructure rather
than growing a membership system inside the application.

## Map the lease table

Add `Elarion.Coordination.PostgreSql` and opt the application's concrete `DbContext` into the model:

```csharp
using Elarion.Coordination.PostgreSql;
using Elarion.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore;

[GenerateDbSets]
[GenerateElarionRoleLeases]
public sealed partial class AppDbContext(DbContextOptions<AppDbContext> options)
    : DbContext(options) {
    protected override void OnModelCreating(ModelBuilder modelBuilder) {
        base.OnModelCreating(modelBuilder);
        ConfigureEntities(modelBuilder); // generated, including elarion_role_leases
    }
}
```

The hand-written model equivalent is `modelBuilder.UseElarionRoleLeases()`. Apply the resulting EF
Core migration before any instance starts competing for a role.

## Register one lease per role

Each registration adds a keyed `IRoleLease` and its heartbeat worker:

```csharp
builder.Services.AddElarionPostgreSqlRoleLease<AppDbContext>(options => {
    options.RoleName = "maintenance";
});
```

Duplicate registration of the same role in one process fails at startup. The defaults are sized so
the old holder stops acting before a successor may legitimately take over:

| Option | Default | Meaning |
| --- | --- | --- |
| `LeaseDuration` | 30 s | How long one successful acquisition remains valid; also the crash-failover bound. |
| `RenewInterval` | 10 s | How often holders renew and non-holders try to acquire. |
| `HeldSafetyMargin` | 5 s | How early local `IsHeld` becomes false before database expiry. |
| `InstanceId` | Machine name + random suffix | Process identity written to the lease row. |
| `AdvertisedAddress` | `null` | Explicit holder address for proxying; otherwise an `IInstanceAddressProvider` may supply it. |

`LeaseDuration` must be greater than `RenewInterval + HeldSafetyMargin`.

Role names are validated against the lease table's 128-character limit during registration. Fixed
partitions validate their generated `{name}:partition-N` roles before adding any services.

## Register a fixed role partition

When a stable key should select one of several coarse roles without configuring process count, register
a fixed partition. One process may hold several partitions; this does not add automatic balancing:

```csharp
builder.Services.AddElarionPostgreSqlRolePartition<AppDbContext>(partition => {
    partition.Name = "devices";
    partition.PartitionCount = 16;
});
```

Resolve the keyed `IRolePartition` (keyed by the partition name) and call `Resolve(key)` (or
`Resolve(scope, key)`) for the locally cached role/holder/address view — no I/O on the hot path:

```csharp
public sealed class DeviceRouter([FromKeyedServices("devices")] IRolePartition partition) {
    public bool OwnsDevice(string deviceId) {
        RolePartitionTarget target = partition.Resolve(deviceId);   // stable hash → one of 16 roles
        return target.IsHeld;   // this process holds the partition's role lease
        // target.Role is e.g. "devices:partition-7"; target.CurrentHolderAddress routes elsewhere.
    }
}
```

Roles are named `devices:partition-0` through `devices:partition-15`. `IRoleLeaseRegistry` exposes all
configured leases to infrastructure such as role-affine outbox claiming.

## Gate every cycle

Resolve the lease by its role name and check `IsHeld` at the start of every unit of work. `IsHeld` is
local, lock-free state; it does not query PostgreSQL on the hot path.

```csharp
using Elarion.Abstractions.Coordination;
using Microsoft.Extensions.DependencyInjection;

public sealed class MaintenanceWorker(
    [FromKeyedServices("maintenance")] IRoleLease lease,
    TimeProvider timeProvider)
    : BackgroundService {

    protected override async Task ExecuteAsync(CancellationToken stoppingToken) {
        while (!stoppingToken.IsCancellationRequested) {
            if (lease.IsHeld) {
                await RunOneCycleAsync(stoppingToken);
            }

            await Task.Delay(TimeSpan.FromSeconds(10), timeProvider, stoppingToken);
        }
    }
}
```

Do not start a permanent leader-only loop in response to a lease-change event. There is deliberately
no such event: database outages fail closed, and a holder can lose the role between any two cycles.
Gate each call or polling cycle instead.

`CurrentHolder` and `CurrentHolderAddress` are diagnostic/routing snapshots refreshed at heartbeat
cadence. They may lag a failover by one renewal interval; correctness comes from `IsHeld`, not from
comparing holder strings.

## Route HTTP to the holder

Some roles own live state or an ordered stream, so every public instance must accept the route while
only the holder may execute it. `Elarion.AspNetCore` ships a small role-holder proxy for that shape:

```csharp
builder.Services.AddElarionInstanceAddress();
builder.Services.AddElarionPostgreSqlRoleLease<AppDbContext>(options => {
    options.RoleName = "maintenance";
});

var app = builder.Build();

// Install before routing/auth so a non-holder never starts local execution.
app.UseElarionRoleHolderProxy("maintenance", "/maintenance", "/maintenance-streams");

app.MapMaintenanceEndpoints();
```

`AddElarionInstanceAddress()` advertises the server's bound address, replacing wildcard hosts with a
non-loopback IPv4 address. Pass an explicit address behind NAT, a reverse proxy, or when nodes use
HTTPS between themselves:

```csharp
builder.Services.AddElarionInstanceAddress("https://app-03.internal:8443");
```

The proxy forwards at most one hop and supports streaming responses such as SSE. It never retries or
queues a request: an unknown/unreachable holder or a failover race returns `503` with
`Retry-After`. The loop guard prevents a forwarded request from bouncing again. When the named lease
is not registered (for example in single-instance development), the call installs no middleware.

The prefix list is intentionally the same rule a future ingress or service mesh would own. When
external routing can target the holder directly, remove the in-app proxy rather than layering both.

For a key-selected role, use the partition overload before routing:

```csharp
app.UseElarionPartitionHolderProxy(
    "devices",
    context => context.Request.Headers["X-Device-Id"].FirstOrDefault(),
    "/device-api");
```

The resolver reads raw path/query/header state. Missing affinity keys return 400; holder failures use
the same bounded 503 behavior as the coarse-role proxy.

When the target subsystem uses scoped affinity, pass that same stable scope. Virtual-sharded actors
hash their logical actor name (the `[Actor(Name = ...)]` value, or the class name without `Actor`) and
canonical key together, so actor ingress must use the scoped overload:

```csharp
app.UseElarionPartitionHolderProxy(
    "actors",
    "Order",
    context => context.Request.Path.Value?.Split('/').LastOrDefault(),
    "/orders");
```

## Actor home is a specialized role

`AddElarionPostgreSqlActorHome<TDbContext>()` composes the same mechanism under the reserved
`"actors"` role for `[Actor(Placement = ActorPlacementMode.SingleHome)]` actors. Calls on other instances fail rather than
forwarding through the actor runtime; host-owned HTTP prefixes can use
`UseElarionRoleHolderProxy("actors", ...)` to reach a single home, or
`UseElarionPartitionHolderProxy("actors", actorName, ...)` for virtual-sharded ingress. See [Actors](/docs/concepts/actors) for
the placement and migration boundaries.

## Failure behavior

- **Graceful shutdown:** the holder releases the row, allowing immediate takeover.
- **Process or node loss:** another instance acquires after `LeaseDuration` expires.
- **Database outage:** no instance considers itself holder after its safety window; coordination
  fails closed.
- **Clock skew:** leases use application clocks. Keep node clocks synchronized; this is not a
  consensus protocol.
- **Two processes on one machine:** the random `InstanceId` suffix keeps their identities distinct.

The full rationale and proxy design are recorded in
[ADR-0049](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0049-role-leases.md) and
[ADR-0050](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0050-role-holder-proxy.md).

## Leased work rows

When an application keeps its own queue-shaped table — outbound e-mail or SMS deliveries, webhook
dispatches, a durable retry table — and workers on any instance must process each row one at a time,
use the leased-work-row primitive from `Elarion.EntityFrameworkCore.LeasedWork`. It is the same claim
the outbox delivers integration events with, packaged so a second table does not re-derive its
invariants from memory:

- **Claim is select → conditional stamp → re-read.** Candidates are read without locks; one
  `ExecuteUpdate` restating the whole eligibility predicate stamps a lease token and expiry onto the rows
  that are still eligible; the worker gets back only the rows carrying its token. Concurrent workers
  never block each other and never receive the same row for the same lease period.
- **Every finalize is lease-guarded.** Completing, failing, releasing, or renewing a row only matches while
  the worker's token is still on it. A worker that stalled past its lease learns it lost the row
  (`false`) instead of overwriting the new owner.
- **Recovery is by expiry.** A crashed worker releases nothing; its lease lapses and the row becomes
  claimable again. There is no reaper and no lock to leak.
- **The claim rides a partial index** over the live rows only, so it stays fast while completed history
  accumulates.

No statement holds a row lock or a transaction across the work itself. That matters most for outbound
delivery: a slow SMTP or HTTP call never pins a database connection, and a producer can still update or
withdraw a row while a worker is busy with it. `SELECT … FOR UPDATE SKIP LOCKED` held across the
external call does the opposite and is deliberately not the pattern.

### Map the table

The entity implements `ILeasedWorkRow` (`Id`, `LockId`, `LockedUntilUtc`) as ordinary properties.
Everything else — the completion marker, the attempt counter, the error, a deadline — stays your own
column:

```csharp
public sealed class Delivery : ILeasedWorkRow {
    public required Guid Id { get; init; }
    public required DateTimeOffset CreatedAtUtc { get; init; }
    public required DateTimeOffset ExpiresAtUtc { get; init; }
    public byte[]? Payload { get; set; }
    public int Attempts { get; set; }
    public DateTimeOffset? CompletedAtUtc { get; set; }
    public string? Error { get; set; }
    public Guid? LockId { get; set; }
    public DateTimeOffset? LockedUntilUtc { get; set; }
}

[EntityConfiguration]
public sealed class DeliveryConfiguration : IEntityTypeConfiguration<Delivery> {
    public void Configure(EntityTypeBuilder<Delivery> entity) {
        entity.ToTable("deliveries");
        // Lease columns plus the partial claim index ix_deliveries_claim over the live queue.
        entity.HasElarionLeasedWork(d => new { d.CreatedAtUtc, d.Id }, "completed_at_utc IS NULL");
    }
}
```

The claim index lists the queue-order column and then `Id`, matching the claim's ordering. The filter is
required. If you keep completed rows for a while, add the complementary purge index yourself.

### Claim, work, finalize

```csharp
private static readonly TimeSpan[] RetryLadder =
    [TimeSpan.FromMinutes(1), TimeSpan.FromMinutes(15), TimeSpan.FromHours(1), TimeSpan.FromHours(12)];

public async Task<int> DeliverBatchAsync(CancellationToken ct) {
    var now = time.GetUtcNow();
    var lockId = Guid.CreateVersion7();
    var claimed = await db.Deliveries.ClaimPendingAsync(new LeasedWorkClaim<Delivery> {
        LockId = lockId,
        NowUtc = now,
        LeaseUntilUtc = now + TimeSpan.FromMinutes(2),   // well above one batch's worth of calls
        BatchSize = 20,
        Eligible = d => d.CompletedAtUtc == null && d.Attempts < 8 && d.ExpiresAtUtc > now,
        OrderBy = rows => rows.OrderBy(d => d.CreatedAtUtc),
        // Count the attempt at claim: a worker that dies mid-call still uses one up.
        OnClaim = s => s.SetProperty(d => d.Attempts, d => d.Attempts + 1),
    }, ct);

    foreach (var delivery in claimed) {
        var outcome = await transport.SendAsync(delivery, ct);   // no lock, no transaction held
        var finished = time.GetUtcNow();
        var owned = outcome.Succeeded
            ? await db.Deliveries.FinalizeClaimAsync(delivery.Id, lockId, s => s
                .SetProperty(d => d.CompletedAtUtc, finished)
                .SetProperty(d => d.Payload, (byte[]?)null), visibleAfterUtc: null, ct)
            : await db.Deliveries.FinalizeClaimAsync(delivery.Id, lockId, s => s
                .SetProperty(d => d.Error, outcome.Error),
                finished + LeasedWorkBackoff.Ladder(delivery.Attempts, RetryLadder, outcome.RetryAfter), ct);
        if (!owned) logger.LogWarning("Delivery {Id} was reclaimed by another worker.", delivery.Id);
    }

    return claimed.Count;
}
```

Run the method from a [scheduled job](/docs/capabilities/scheduling) or a `BackgroundService` loop on
every instance; the claim makes that safe. A failed attempt's finalize sets the retry visibility
(`LeasedWorkBackoff.Exponential`, or `LeasedWorkBackoff.Ladder`, which honors a longer remote
`Retry-After`), so a failing row waits instead of blocking the head of the queue. `ReleaseClaimAsync`
hands back a row without bookkeeping, and `RenewClaimAsync` extends the lease for work that can outlive it.

Delivery stays **at least once**: a worker that crashes after the remote side accepted but before the
finalize leaves the row to be retried. Give the remote side the row `Id` as its idempotency key where it
accepts one.

### Giving up, guarding the outcome, and shutting down

Four needs recur in every worker; the primitive answers each so the skeleton is not rewritten per queue:

- **Give up an exhausted row at claim.** `Exhausted` names rows that have used up their attempts — evaluated right
  after the stamp, on the values `OnClaim` wrote, so `d => d.Attempts > MaxAttempts` also catches a row whose every
  previous worker died mid-call. Such a row is not returned: it is finalized at once with `GiveUp` (which must take
  it out of `Eligible`) and reported to `OnGivenUp` for logging. Without it, an exhausted row just sits in the table.
  Every given-up row is reported, even after a callback threw; a failed report fails the claim, and the won rows are
  released first instead of staying stamped until their lease lapses. A claim can therefore come back empty while
  work remains — every candidate given up or taken by another worker — so an empty claim is not "queue drained".
- **Write the outcome only while it still applies.** Work done without a lock can race a concurrent writer. A
  `LeasedWorkFinalize<TRow>` with `StillEligible` applies the setters only while the row still meets that condition;
  otherwise the claim is ended without them. The outcome says which happened (`Finalized`, `Ineligible`, `ClaimLost`).
  `Ineligible` clears the lease at once and ignores `VisibleAfterUtc`: that backoff belonged to the discarded result,
  and the concurrent writer's values decide through `Eligible` whether the row is still work.
- **Give a batch back on shutdown.** `ReleaseClaimsAsync(ids, lockId, update, ct)` ends the claims on the unfinished
  rows in one statement and lets the update take back the attempt the claim counted — it was never made.
- **Read related data with the claim.** `ClaimPendingAsync(claim, select, ct)` projects the won rows in the same
  query (`m => new { m.Id, m.Attempts, m.Attachment.BlobId }`) instead of a second query per batch.

```csharp
var claimed = await db.ImageMetadata.ClaimPendingAsync(new LeasedWorkClaim<ImageMetadata> {
    LockId = lockId, NowUtc = now, LeaseUntilUtc = now + Lease, BatchSize = 20,
    Eligible = m => m.State == ReadState.Pending,
    OrderBy = rows => rows.OrderBy(m => m.UploadedAt),
    OnClaim = s => s.SetProperty(m => m.Attempts, m => m.Attempts + 1),
    Exhausted = m => m.Attempts > MaxAttempts,
    GiveUp = s => s.SetProperty(m => m.State, ReadState.Done).SetProperty(m => m.Error, "attemptsExhausted"),
    OnGivenUp = (m, _) => { logger.LogWarning("Metadata of {Id} given up.", m.Id); return ValueTask.CompletedTask; },
}, m => new { m.Id, m.Attempts, m.Attachment.BlobId }, ct);

var finished = 0;
try {
    foreach (var row in claimed) {
        var read = await ReadAsync(row.BlobId, ct);
        // Only while still pending: a newer upload meanwhile wrote its own values and marked the row done.
        await db.ImageMetadata.FinalizeClaimAsync(row.Id, lockId, new LeasedWorkFinalize<ImageMetadata> {
            Update = s => s.SetProperty(m => m.Width, read.Width).SetProperty(m => m.State, ReadState.Done),
            StillEligible = m => m.State == ReadState.Pending,
        }, ct);
        finished++;
    }
}
catch (OperationCanceledException) when (ct.IsCancellationRequested) {
    // The pass's token is cancelled: give the rest back on a fresh one, attempt uncounted.
    await db.ImageMetadata.ReleaseClaimsAsync(claimed.Skip(finished).Select(r => r.Id), lockId,
        s => s.SetProperty(m => m.Attempts, m => m.Attempts - 1), CancellationToken.None);
    throw;
}
```

### Testing a worker

The claim and every finalize are `ExecuteUpdate` statements, which EF InMemory cannot run — and InMemory would hide
the concurrency the primitive exists for anyway. Test a worker against PostgreSQL with a Testcontainers fixture, the
way Elarion tests the primitive itself: create the schema once per fixture, give every test its own rows (a per-test
marker column in `Eligible`, like a source or tenant id, keeps tests in one table apart), and pass `NowUtc`
explicitly so lease expiry and backoff are exact without waiting. Two workers racing for one batch are two contexts
on the same fixture.

The invariants and the extraction history are recorded in
[ADR-0073](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0073-leased-work-rows.md).

## Row and advisory locks

Most concurrency is the database's job — constraints, optimistic concurrency, `ON CONFLICT`. Some rules are not
expressible as a constraint: "periods of one unit never overlap" across a whole set, a read-then-write that must not
interleave with another writer of the same aggregate. For those, `Elarion.EntityFrameworkCore.UnitOfWork` adds two
**transaction-scoped** PostgreSQL locks on `DbContext`, held until the current transaction (a command's pipeline
transaction, or one you opened) commits or rolls back:

```csharp
using Elarion.EntityFrameworkCore.UnitOfWork;

// Lock one row; table and key column come from the EF model. False when no visible row has that key.
if (!await db.LockRowAsync<LeaseUnit>(command.UnitId, RowLockMode.NoKeyUpdate, ct))
    return AppError.NotFound("No such unit.");

// No row to lock (the account may not exist yet): lock a key instead, or try without waiting.
await db.AdvisoryLockAsync("billing-account", command.AccountNumber, ct);
var period = command.Period.ToString("yyyy-MM", CultureInfo.InvariantCulture);
if (!await db.TryAdvisoryLockAsync("statement-run", period, ct))
    return AppError.Conflict("A statement run for this period is already in progress.");
```

`LockRowAsync` looks the row up through the entity's own set first, so its query filters (tenant scoping, soft
delete) and a hierarchy's discriminator apply: a row the context cannot see answers `false` and is never locked, so an
id from a request cannot probe or stall another tenant's row. A strongly typed key with a value converter is converted
the way EF converts it; an id of another type throws `ArgumentException`.

A writer that deliberately changes rows its filters hide, such as an archived tenant, locks past them with the options
overload. Every filter is skipped, tenant scoping included, so use it only for an id the handler has already
authorized:

```csharp
if (!await db.LockRowAsync<Tenant>(command.TenantId,
        new RowLockOptions { Mode = RowLockMode.NoKeyUpdate, IgnoreQueryFilters = true }, ct))
    return AppError.NotFound("No such tenant.");
```

| `RowLockMode` | SQL | Choose it when |
| --- | --- | --- |
| `Update` (default) | `FOR UPDATE` | a concurrent insert of a row *referencing* this one (a foreign key) must wait too — deleting a role against a concurrent assignment of it |
| `NoKeyUpdate` | `FOR NO KEY UPDATE` | only writers of the row itself must be serialized; inserts referencing it proceed |
| `Share` | `FOR SHARE` | readers may share; writers wait |
| `KeyShare` | `FOR KEY SHARE` | only a change of the row's key or its deletion waits |

Both refuse to run **outside a transaction** (PostgreSQL would release the lock at the end of its own statement) and
on any provider other than PostgreSQL, so a lock never silently protects nothing. An ambient `TransactionScope` counts
as a transaction because the connection enlists in it; a connection string with `Enlist=false` opts out of that, so
lock inside an EF or pipeline transaction on such a connection. Tests of locking run against
PostgreSQL ([Testcontainers](/docs/concepts/persistence-and-transactions#testing-persistence)).

A unit test on another provider that only passes through a lock, such as a handler test on EF InMemory or SQLite,
opts its own context out explicitly:

```csharp
var options = new DbContextOptionsBuilder<AppDbContext>()
    .UseInMemoryDatabase(Guid.CreateVersion7().ToString())
    .UseUnenforcedElarionLocks()   // locks lock nothing; the provider and transaction checks are skipped
    .Options;
```

On that context the helpers still validate keys and scopes, and `LockRowAsync` still answers whether a visible row has
the key, so the handler's not-found path runs as in production. A context without the opt-in still fails closed. A
PostgreSQL context that carries it throws at its first lock, so a shared test options helper can't leave a real
database unlocked.

### One advisory key scheme

A database has one advisory-lock space. Every advisory lock taken through Elarion locks
`hashtextextended('scope:key', 0)` — `AdvisoryLockKey.Text(scope, key)` builds the text, the same function the
framework uses — so two `(scope, key)` pairs only meet when their hashes collide. A scope names what is serialized
(`billing-account`) and must not contain `:`. Scopes starting with `elarion.` are reserved; the framework locks:

| Scope | Key | Taken by |
| --- | --- | --- |
| `elarion.scheduler.job` | the job name | the multi-node scheduler's window claim |
| `elarion.devices.pairing` | the device id | reissuing a device's pairing code |

The migration runner's session-level lock uses its own fixed key (`PostgreSqlMigrationRunner.DefaultAdvisoryLockKey`),
not a hashed text. A host on the EF-free SQL tier builds the same text with `AdvisoryLockKey.Text` and runs
`SELECT pg_advisory_xact_lock(hashtextextended($1, 0))` itself.

<Callout type="info">
A lock is per transaction, not per node or per process: it serializes the transactions that ask for it on the one
PostgreSQL every instance shares, and it ends with the transaction. For "exactly one instance does this for a long
time", use a role lease; for "one worker per queue row", use leased work rows.
</Callout>
