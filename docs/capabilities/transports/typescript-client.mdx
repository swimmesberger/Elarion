---
title: TypeScript client
description: Generate typed method contracts, Zod result schemas, and a portable fetch client from an exported rpc-schema.json.
---

`elarion-jsonrpc-client-generator` turns an exported [`rpc-schema.json`](/docs/capabilities/transports/schema-generation)
into a typed TypeScript client. The frontend gets full type safety and runtime validation without
hand-writing DTOs, and the generated runtime stays portable across browsers and Node.js.

## Generating the client

```bash
npm install --save-dev @swimmesberger/elarion-jsonrpc-client-generator
npx elarion-jsonrpc-client-generator --schema rpc-schema.json --out src/generated
```

It always emits the three core files, plus conditional outputs when the schema calls for them:

| File | Purpose |
| --- | --- |
| `rpc-types.ts` | `RpcMethods` interface mapping method names to params/result types. |
| `rpc-schemas.ts` | `rpcParamsSchemas` and `rpcResultSchemas` Zod maps for runtime params/result validation, plus the [limits, presets, sort keys and constants](#limits-presets-sort-keys-and-constants) the schema declares. |
| `rpc-client.ts` | Typed fetch client for single calls and batches. |
| `session-client.ts` | Client-capability snapshot client and OpenFeature provider — emitted **only** when the schema exposes the `elarion.session` operation (rename it with `--session-client <file>`). |
| `events-client.ts` | Topic-typed [client-event subscription client](#client-event-subscriptions) — emitted **only** when the schema declares client-event topics. |

An opt-in [`start-adapter.ts`](#tanstack-start) joins them under `--framework tanstack-start`. A schema
that declares neither session nor events produces byte-identical output to before — the conditional
files simply do not exist.

The schema and client files import `zod` (v3 and v4 are both supported), so install it as a runtime
dependency in the consuming app.

The generated files import each other with `.js` specifiers (`from './rpc-schemas.js'`), which a bundler and `tsc`
under `moduleResolution: NodeNext` resolve to the `.ts` files. Plain Node does not: to load the generated modules
without a build step — a module that calls `decisionQuestion` under `node --test`, a script — generate with
`--import-extension ts` (`importExtension: 'ts'`), which names the `.ts` files themselves. Node runs them with its
type stripping (unflagged since Node 23.6); `tsc` then needs `allowImportingTsExtensions` with `noEmit`, or
`rewriteRelativeImportExtensions`.

<Callout type="warn">
  **Pin the generator to the backend's version.** The npm `latest` dist-tag tracks stable releases and
  can lag behind the backend packages, which publish a `-preview.N` build from every push to `main`.
  When your host runs a preview version, install the **matching exact preview version** of the
  generator rather than a `^` range — otherwise the generator reads a newer `rpc-schema.json` with an
  older code path and silently emits less than the schema describes (a missing emitted file such as
  `session-client.ts`, or absent params schemas, are the usual symptoms):

  ```bash
  # Substitute the exact version your host's Elarion packages resolve to —
  # the full preview string, e.g. <major>.<minor>.<patch>-preview.<run>.<attempt>
  npm install --save-dev --save-exact \
    @swimmesberger/elarion-jsonrpc-client-generator@<backend-version>
  ```

  Move both sides together: bump the backend packages and the generator in the same change.
</Callout>

The emitted Zod schemas are **constraint-aware**: the DataAnnotations attributes on the server's
request DTOs flow through the exported schema into the client (see
[Validation](/docs/concepts/validation)) — `minLength`/`maxLength` become `.min()`/`.max()`,
`pattern` becomes `.regex(new RegExp(...))`, `minimum`/`maximum` become `.gte()`/`.lte()` (exclusive
bounds `.gt()`/`.lt()`), `minItems`/`maxItems` become array `.min()`/`.max()`, integers get `.int()`,
and the `uuid`/`email`/`uri` formats become `.uuid()`/`.email()`/`.url()`.

An attribute's explicit message (`x-elarion-error-messages`, see
[Error messages](/docs/concepts/validation#error-messages)) becomes the check's message argument, so the
local failure reads like the server's:

```ts
code: z.string().max(20, "Code must be at most 20 characters.").regex(new RegExp("^[A-Z]{3}$"), "Code must be three capital letters."),
mode: z.enum(["fast", "slow"], { message: "Pick fast or slow." }),
```

Checks take the plain-string message and schema constructors (`z.enum`, `z.literal`, `z.union`) take
`{ message }` — the forms Zod v3 and v4 share. One difference remains on Zod v3: it applies a constructor
message to `z.enum` but not to the `z.literal`/`z.union` emitted for a non-string `[AllowedValues]`, which keeps
Zod's default text there. Constraints without an explicit message keep Zod's default text on both versions.

### Watch mode

For a tight dev loop, pass `--watch` to regenerate whenever `rpc-schema.json` changes:

```bash
npx elarion-jsonrpc-client-generator --schema rpc-schema.json --out src/generated --watch
```

It generates once, then watches the schema file and regenerates on every write — surviving the transient
states a build tool leaves the file in mid-write (a partial or momentarily-invalid schema is logged and
skipped, never fatal). Paired with a server that re-exports the schema on save, an edit to a C# handler
flows straight to the typed frontend:

```bash
# terminal 1 — API: re-export rpc-schema.json on every change (see Schema generation)
dotnet watch

# terminal 2 — regenerate the TS client whenever the schema lands
npx elarion-jsonrpc-client-generator --schema ../api/rpc-schema.json --out src/generated --watch
```

The two stay decoupled: the .NET build owns [schema export](/docs/capabilities/transports/schema-generation),
the generator owns the client — no Node/npm dependency is baked into the server build. For a permanent setup,
wire the watch command into a `package.json` script (e.g. `"rpc:watch"`).

## Calling methods

Dotted JSON-RPC method names become nested properties, so `clients.get` is `rpc.clients.get(...)`:

```ts
import { createRpcApi } from './generated/rpc-client'

const rpc = createRpcApi({
  url: '/rpc',
  headers: { Authorization: `Bearer ${token}` },
})

const abort = new AbortController()
const client = await rpc.clients.get({ id }, { signal: abort.signal })
```

The client uses `globalThis.fetch` in browsers and modern Node.js. The lower-level
`createRpcClient(...)` generic transport is also exported for advanced cases.

## File payloads map to native `File`

A handler parameter or result typed [`ElarionFile`](/docs/capabilities/transports/json-rpc#file-payloads)
is exported with an `x-elarion-file` marker, and the generated client surfaces it as a **native `File`**
on both sides — the base64 wire envelope never leaks into application code:

```ts
// Upload: pass the File from an <input type="file"> straight through.
const receipt = await rpc.documents.import({ container: 'invoices', file: input.files[0] })

// Download: the result is a real File (name, type, bytes) — hand it to URL.createObjectURL.
const exported = await rpc.exports.get({ list: 'clients' })
window.open(URL.createObjectURL(exported))
```

Params validate the `File` instance (Zod `z.instanceof(File)`); the client encodes it to the base64
envelope after validation and decodes result envelopes back into `File` objects before validation — so
the conversion also runs when validation is disabled. Everything used is standard in browsers and Node
20+; schemas without file payloads generate byte-identical output. Remember `ElarionFile` is the
small-file tier — for large uploads use [uploaded files](#uploaded-files), for large downloads the
[staged-blob flows](/docs/capabilities/blob-uploads#streaming-downloads-and-temp-file-flows).

## Uploaded files

A handler member typed [`UploadedFile`](/docs/capabilities/blob-uploads#passing-an-upload-to-a-handler) travels as
the blob id of a staged upload and is exported with an `x-elarion-upload` marker. The generated client types it
`File | Blob | UploadedFileRef` in params and `UploadedFileRef` (an exported `string` alias in `rpc-types.ts`) in
results. Pass a `File` and the client uploads it before the call, then sends the reference:

```ts
// One call: the client streams the file to the upload endpoint, then calls the method with its reference.
const analysis = await rpc.statements.analyze({ statement: input.files[0] })

// A multi-step flow: upload once, pass the reference to every step.
const statement = await rpc.$uploadFile(input.files[0])
const preview = await rpc.statements.preview({ statement, mapping })
await rpc.statements.commit({ statement, mapping })
```

The default uploader POSTs the raw file to the direct-upload endpoint (`MapElarionBlobUploads`) with the client's
`fetch` and `headers` (a `headers` function sees an empty `methods` list), its `type` as `Content-Type` and its name in
`X-Elarion-File-Name` (or the `fileName` query parameter for a name outside printable ASCII), and reads the reference
from the `text/plain` answer. It posts to `/_elarion/blobs` on the origin of `url`, or relative to the page for a
relative `url`; the call's `AbortSignal` cancels its uploads too. Two client options change that:

```ts
const rpc = createRpcApi({
  url: '/api/rpc',
  uploadUrl: '/api/_elarion/blobs',                 // a host that mounts the endpoints under a path base
  uploadFile: (file, { fileName, signal }) => tusUpload(file, { fileName, signal }),   // any uploader → reference
})
```

`$uploadFile(file, { policy, resourceId })` stages the file under an
[upload policy](/docs/capabilities/blob-uploads#upload-policies-a-larger-limit-for-one-kind-of-upload) — a larger
limit for one kind of upload, checked against the record it is for — and the default uploader sends both as query
parameters; a configured `uploadFile` receives them in its options. Staging the `File` params of a call uses no policy,
so a member that needs one is uploaded with `$uploadFile` first and called with the reference.

`$uploadFile(file, { fileName, signal })` (also `$client.uploadFile`) names a `Blob` that has no name of its own. Params
validation accepts a `Blob` or a string at an upload position, before the upload. When the member declares
[`[UploadLimits]`](/docs/capabilities/blob-uploads#declaring-the-limits-on-the-member), the `Blob` must also fit them:
a larger file, another media type or a name without an accepted extension fails params validation with the server's
message (`RpcParamsValidationError`) and is never uploaded. The media type is compared as the server compares it —
case-insensitively, parameters ignored, an untyped `Blob` as `application/octet-stream` — and the extension against the
end of the file's name, case-insensitively (a `Blob` has no name). A reference passes; the server checks the file it
names. A failed upload rejects the call with `RpcTransportError` and the method is not called. A retry that passes the
`File` again uploads it again and sends a new reference, so for an `[Idempotent]` operation upload once with
`$uploadFile` and retry with the reference — otherwise the retried request differs from the first one and answers
`idempotency.key_reused`. Schemas without upload members generate byte-identical output.

### Upload limits in the user's language

A refused file is reported by error code with the limit as data, never only as English text, on every path:

- **The server** answers `upload.too_large` with `{ maxBytes, length }`, `upload.content_type` with
  `{ contentTypes, contentType }` and `upload.file_extension` with `{ fileExtensions, fileName }`. A method whose request
  declares `[UploadLimits]` has those codes in its contract, so `isRpcMethodError(method, error)` narrows `error.data` by
  `error.code`.
- **`$uploadFile(file, { method, member })`** checks the file against the limits of that method's upload member before
  uploading it and throws `RpcUploadLimitError`: an `RpcError` with the code, message and data the server would answer,
  plus `method` and `member`. One handler words both. The pair is typed — `method` is a method that takes an upload,
  `member` one of its upload members by path (a list by its own path) — and the check is skipped when
  `validateParams` is `false`.
- **Params validation** before a call adds the code and the limit to the Zod issue as `params`
  (`{ code: 'upload.too_large', maxBytes }`, likewise `contentTypes` and `fileExtensions`), so a Zod error map words it;
  `RpcParamsValidationError.cause` carries the issues.

```ts
try {
  const workbook = await rpc.$uploadFile(file, { method: 'contacts.import', member: 'workbook' })
  await rpc.contacts.import({ workbook })
} catch (error) {
  if (!isRpcMethodError('contacts.import', error)) throw error
  switch (error.code) {   // the client's check and the server's answer alike
    case 'upload.too_large':
      return showError(t('upload.tooLarge', { max: formatBytes(error.data.maxBytes) }))
    case 'upload.file_extension':
      return showError(t('upload.extension', { accepted: error.data.fileExtensions.join(', ') }))
    default:
      return showError(error.message)
  }
}
```

`rpcUploadLimits` in `rpc-schemas.ts` lists every upload member of each method with its declared `maxBytes`,
`contentTypes` and `fileExtensions` (`{}` when it declares none); `$uploadFile` reads it, and a page can build an
`<input accept>` from it.

## C# unions map to TypeScript unions

On .NET 11 a request or response property can be a C# 15 union. System.Text.Json writes the active case with no
wrapper or discriminator and exports the union as `anyOf`, one schema per case; the generator turns that into a
TypeScript union and a Zod `z.union`:

```csharp
public sealed record Found(string Name, int Stock);
public sealed record Missing(int Reason);

[JsonUnion(TypeClassifier = typeof(JsonUnionTypeStructuralClassifier))]
public union ProductLookup(Found, Missing);

public sealed record Response(ProductLookup Result);
```

```ts
// rpc-types.ts
result: { name: string; stock: number } | { reason: number }
// rpc-schemas.ts
result: z.union([z.strictObject({ ... }), z.strictObject({ ... })])
```

- **Object cases need a classifier on the server.** Out of the box System.Text.Json picks a case by JSON token kind
  only, so a union of two object cases cannot be deserialized. `JsonUnionTypeStructuralClassifier` picks the case by
  its property names; give each case a property the others lack (or mark distinguishing properties `required`).
- **Object cases are strict on the client.** They are emitted as `z.strictObject`, so like the server's classifier a
  payload carrying another case's property matches no case instead of being stripped into the first one.
- **Nullability follows the declaration**, like any other property: a `ProductLookup` property is required, a
  `ProductLookup?` one optional and nullable. A `default` union holds no case and serializes as `null`, so give a
  non-nullable union property a value.
- **Not inside unions:** [file payloads](#file-payloads-map-to-native-file) and [uploaded files](#uploaded-files) —
  which case is active is only known per value, so the client could not convert them at a fixed path; the generator
  rejects that schema.

Validation attributes on the case types are enforced on the active case, at the property's path
(see [Validation](/docs/concepts/validation)).

## Batching

Batch requests are built through generated `$request` helpers and preserve input order even when the
server responds out of order. Each item resolves independently, so one failure does not reject the
whole batch:

```ts
const [clientResult, projectsResult] = await rpc.$batch([
  rpc.$request.clients.get({ id }),
  rpc.$request.projects.list({ clientId: id }),
] as const)
```

## Client-event subscriptions

When the schema declares an `events` block (the host registers
[client-event topics](/docs/capabilities/events/client-events)), the generator also emits
`events-client.ts`: a topic-typed subscription client that multiplexes every subscription over one
`EventSource`, validates payloads with the same generated Zod schemas, and exposes
`$client.onConnected` as the "re-query now" signal. A connection the `EventSource` gave up on (a 401, a login
page, a 502 mid-deploy) is reopened with a backoff (`reconnectDelay`). A schema without events produces
byte-identical output — the file simply doesn't exist.

```ts
import { createElarionEvents } from './generated/events-client.js'

const events = createElarionEvents({ url: '/events' })
events.invoicing.invoiceChanged.subscribe((evt) => refetch(evt.invoiceId))
```

## Server-side and SSR usage

Pass an injected `fetch` and dynamic headers for SSR, edge, or server-function deployments — for
example to forward request-scoped authentication without forking the generated client:

```ts
const rpc = createRpcApi({
  url: process.env.API_INTERNAL_URL + '/rpc',
  fetch,
  headers: () => ({ Authorization: `Bearer ${forwardedJwt}` }),
  transformResult: normalizeRpcResultForSchema,
})
```

### TanStack Start

During SSR you usually need to forward the incoming request's `cookie` (or another identity header) so the RPC
call runs as the signed-in user. Generate with `--framework tanstack-start` to emit an **opt-in** `start-adapter.ts` next to
the neutral core client (it needs the `@tanstack/react-start` peer dependency):

```bash
npx elarion-jsonrpc-client-generator --schema rpc-schema.json --out src/generated --framework tanstack-start
```

`createStartRpcApi` is a turnkey `createRpcApi` with request-scoped cookie forwarding pre-wired; any
`headers` you pass are layered on top:

```ts
import { createStartRpcApi } from './generated/start-adapter'

export const rpc = createStartRpcApi({ url: '/rpc' })
```

#### Forwarding other request headers

An app behind an authenticating reverse proxy (Cloudflare Access, Google IAP, oauth2-proxy, …) authenticates
from a header the proxy sets on the incoming request rather than from a cookie, and an SSR call to the API has to
carry that header too. Name the headers to forward with `forwardHeaders`:

```ts
export const rpc = createStartRpcApi({
  url: '/rpc',
  forwardHeaders: ['cookie', 'cf-access-jwt-assertion'], // e.g. Cloudflare Access
})
```

The list **replaces** the default `['cookie']` — keep `'cookie'` in it when the session cookie should still travel,
and pass `[]` to forward nothing. Names match case-insensitively and are sent lower-case; a header the incoming
request does not carry is skipped. In the browser nothing is forwarded (the browser attaches its own cookies), and
explicitly passed `headers` win over a forwarded header of the same name. Forward identity and correlation headers
only, never hop-by-hop or framing headers such as `host`, `connection`, or `content-length`.

For finer control the adapter also exports the isomorphic headers functions on their own —
`forwardRequestHeaders(names)` and `forwardRequestCookie` — so you can compose them into a plain `createRpcApi`
call, or into any other `fetch`-based client that runs during SSR:

```ts
import { createRpcApi } from './generated/rpc-client'
import { forwardRequestHeaders } from './generated/start-adapter'

const rpc = createRpcApi({ url: '/rpc', headers: () => forwardRequestHeaders(['cookie', 'authorization']) })
```

#### The status of a failed SSR render

A page rendered on the server answers `200` unless something sets another status, so a page whose loader met a
refusal would answer `200` with the error view. The adapter exports what a server entry needs to answer the right
status: `ssrStatusFor(error)` maps an error to `401`, `403` or `404` for the server's unauthorized, forbidden and
not-found answers, to `503` when the service (or the platform or proxy in front of it) answered `503 Service
Unavailable` — maintenance, a stopped installation — and to `undefined` otherwise; `withResponseStatus(response,
status)` returns the rendered response with that status (the body streams unchanged, and a `503` gets
`Cache-Control: no-store` unless it states one). Record the error a loader or error boundary met in a place your
server entry can read for the request, then rewrite:

```ts
import { ssrStatusFor, withResponseStatus } from './generated/start-adapter'

const response = await render(request)
const status = ssrStatusFor(renderError(request)) // the error your loader or boundary recorded for this request
return status === undefined ? response : withResponseStatus(response, status)
```

In the page itself, `isServiceUnavailable(error)` (from the core client, also through a mapped error's `cause`) tells
a "back soon" state from a failure.

<Callout type="warn">
  The header read must stay inside `createIsomorphicFn().server(...)`. Importing `@tanstack/react-start/server`
  from any module the client bundle can reach — even a dynamic import behind a `typeof window` guard — fails
  `vite build` with `[import-protection] Import denied`. The emitted adapter is structured so the Start
  compiler strips the import (and the read) from the client build; keep that shape if you hand-roll it instead.
  Because the frontend rarely rebuilds in CI, this is easy to get wrong unnoticed.
</Callout>

## Error handling

A JSON-RPC error returned by the server is thrown as a typed `RpcError`. Every error carries a stable string
`code` (the contract to branch on, for example `not_found` or `token.malformed`), a typed `data` payload, the
human-readable `message`, and `rpcCode` — the numeric JSON-RPC code, which only encodes the coarse `AppError` kind
and is why it is not called `code`. The wire shape is always `error.data = { code, data? }`
([ADR-0080](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0080-errors-are-a-declared-contract-with-a-stable-code.md)).

Handlers declare the errors they produce with `[ProducesError]` (on the handler, or once on a decorator, module or
assembly for errors that many operations share), and the generator emits them per method: each
method's `errors` entry in `RpcMethods` maps a code to its kind and payload type, and the client exports
`RpcMethodError<M>`, a union of `RpcError` variants discriminated by `code`, with `data` typed per variant:

```ts
import { isRpcMethodError, type RpcMethodError } from './generated/rpc-client'

function describe(error: RpcMethodError<'tokens.redeem'>) {
  switch (error.code) {
    case 'token.malformed':
      return `Malformed: ${error.data.reason}` // data is typed from the declared payload
    case 'not_found':
      return 'Unknown token'
  }
}

try {
  await rpc.tokens.redeem({ token })
} catch (error) {
  if (isRpcMethodError('tokens.redeem', error)) return describe(error) // narrows by the declared codes
  throw error
}
```

A declared payload is validated against its generated Zod schema (`rpcErrorDataSchemas`) unless
`validateResults: false`; a mismatch throws `RpcProtocolError` instead of surfacing a mistyped error. Batch items
report `error: RpcError`; narrow them with `isRpcMethodError`. Without a `{ code, data }` envelope (a foreign
server) `code` falls back to the default code of the numeric kind.

Beyond the standard JSON-RPC codes, Elarion maps its transport-agnostic `AppError` kinds
onto the server-reserved range, and the generated `RpcError` exposes a getter per kind (reading `rpcCode`) — a
quick way to branch on the kind alone:

```ts
import { RpcError, ElarionErrorCodes } from './generated/rpc-client'

try {
  await rpc.clients.get({ id })
} catch (error) {
  if (error instanceof RpcError) {
    if (error.isNotFound) return renderNotFound()
    if (error.isForbidden || error.isUnauthorized) return redirectToLogin()
    if (error.isConflict) return showConflictToast(error.message)
  }
  throw error
}
```

| Getter | Code | `AppError` kind |
| --- | --- | --- |
| `isInvalidParams` | `-32602` | `Validation` |
| `isNotFound` | `-32001` | `NotFound` |
| `isConflict` | `-32002` | `Conflict` |
| `isForbidden` | `-32003` | `Forbidden` |
| `isBusinessRule` | `-32004` | `BusinessRule` |
| `isUnauthorized` | `-32005` | `Unauthorized` |
| `isDecisionRequired` | `-32006` | `DecisionRequired` |
| `isInternalError` | `-32603` | `Internal` |

The application codes are also exported as `ElarionErrorCodes` for `switch` statements, and the standard
JSON-RPC getters (`isParseError`, `isInvalidRequest`, `isMethodNotFound`) stay available. These codes are
the framework default from [`AppErrorMapper`](/docs/reference/result-and-errors); a host that registers a
custom `IAppErrorTranslator<RpcError>` changes the wire codes, so keep the frontend aligned. A network or
HTTP-level failure throws `RpcTransportError` and a malformed JSON-RPC envelope throws `RpcProtocolError`.

### Timeouts, error mapping and retries

`RpcClientOptions` bounds every request and gives the application one place to word failures:

```ts
import { createRpcApi, isRetryable, RpcError, RpcTimeoutError } from './generated/rpc-client'

export const rpc = createRpcApi({
  url: '/rpc',
  timeoutMs: 30_000,                                        // every request
  timeoutFor: (method) => method === 'reports.export' ? 180_000 : undefined,
  mapError: (error) => new AppFailure(localize(error), { cause: error }),
})

// TanStack Query: retry only what a retry can clear.
const queryClient = new QueryClient({
  defaultOptions: { queries: { retry: (count, error) => count < 3 && isRetryable(error) } },
})
```

- **Timeouts.** A request still unanswered after its timeout is aborted and throws `RpcTimeoutError` (`timeoutMs`,
  `methods`). The timeout of a method is, first to last: the call's `timeoutMs` option (`false` sends it without
  one), `timeoutFor(method)`, the handler's `[ClientTag("timeout", "180s")]` (`rpcMethodInfo[m].tags.timeout`, in
  `ms`, `s` or `m`; a bare number is seconds), and the client's `timeoutMs`. A batch waits for the longest of its
  methods. The caller's own `AbortSignal` still cancels, and its abort is never reported as a timeout.
- **Error mapping.** `mapError(error, context)` receives every error a call or batch throws — `RpcError`,
  `RpcTransportError`, `RpcTimeoutError`, a params or protocol error, a network failure — and what it returns is
  thrown instead (`undefined` keeps the original). Keep the original as `cause`: `isRetryable`,
  `isServiceUnavailable` and the decision helpers look through it. The errors inside a batch's item results are not
  mapped.
- **Retries.** `isRetryable(error)` is true for a network failure, a timeout, a `408`, `429` or `5xx` transport
  answer, an unexpected server error (`code: "internal"`) and `idempotency.in_progress`, and false for every answer
  the server decided (validation, not found, conflict, forbidden, unauthorized, business rule, a decision), a params
  or protocol error and a call the caller aborted.

An unexpected server error (an exception, `code: "internal"`) carries a support reference in `error.reference` —
the server's configured [unexpected-error](/docs/concepts/results-and-errors#unexpected-errors) answer. Show it next
to the message instead of matching the message text; it is `undefined` for every other error:

```ts
if (error instanceof RpcError && error.code === 'internal')
  return showError(`${error.message} (reference ${error.reference ?? 'unavailable'})`)
```

### Answering decisions

A method whose handler declares [`[RequiresDecision]`](/docs/concepts/results-and-errors#asking-the-caller-to-decide)
lists each decision in its `errors` with kind `decision_required`, its `options` and `perItem`, and its request's
`decisions` member is typed with exactly those answers: a declared code, one of its options, and for a per-item
decision the item. An undeclared code or option is a compile error, and the generated params schema rejects it before
the call is sent:

```ts
// RpcParams<'banking.imports.commit'>['decisions'], also available as RpcMethodDecisionAnswer<M>[]
decisions?: (
  | { code: 'banking.closed_period'; option?: 'confirm' }                              // a confirmation
  | { code: 'banking.possible_duplicate'; item: string; option: 'import' | 'skip' }    // a choice per item
)[] | null
```

`withDecisions` runs the call; when the server needs a decision the method declares, it hands your dialog a typed
question and calls again with the answer added to `decisions`, until the call succeeds or fails otherwise:

```ts
import { withDecisions } from './generated/rpc-client'

const outcome = await withDecisions(client, 'banking.imports.commit', { statement }, async (question) => {
  switch (question.code) {
    case 'banking.closed_period':
      return (await confirm(question.message)) ? 'confirm' : undefined   // undefined cancels
    case 'banking.possible_duplicate':
      // perItem: one option per item key the data lists, typed "import" | "skip"
      return await askPerLine(question.data.lines)                       // Record<string, 'import' | 'skip'>
  }
})
```

The question carries `code`, `message`, the declared `options`, `perItem`, the typed `data` and the `RpcError`.
Returning `undefined` cancels: `withDecisions` throws `RpcDecisionCancelledError` (with the `question` and, as its
`cause`, the decision error), so a caller tells a cancel from a failure of the call. The first call sends the params
as given, without an empty `decisions` list. A later answer for the same code and item replaces an earlier one, and `maxQuestions`
(default 10) stops a server that keeps asking. Each resend is a new request, so an idempotent method gets a new
idempotency key unless the options fix one.

The first argument is the generated client or your own call seam, any function shaped
`(method, params, options?) => Promise<result>` (`RpcCall<M>`), so the calls keep going through the timeouts,
error mapping and localization of your application:

```ts
const outcome = await withDecisions(rpc, 'banking.imports.commit', { statement }, askImportDecision)
```

When the dialog is declarative state rather than an awaited promise (its saving state and the resend's failure shown
inside it, a query library's mutation sending the call), use the two primitives `withDecisions` is built on:
`decisionQuestion(method, error)` recognizes a question the method declares and returns it typed (or `undefined` for
any other error), and `answerDecision(decisions, question, answer)` returns the request's `decisions` with the answer
added, replacing an earlier answer for the same code and item:

```ts
import { answerDecision, decisionQuestion } from './generated/rpc-client'

// When the call fails: keep the question and the params it answers.
const question = decisionQuestion('banking.imports.commit', error)
if (question) setPending({ question, params })

// When the user answers: resend through your own mutation, with the answer added.
commit.mutate({ ...pending.params, decisions: answerDecision(pending.params.decisions, pending.question, answer) })
```

Both recognize the `RpcError` itself or an error whose `cause` chain holds it, so a seam that wraps errors keeps working.
`withDecisions`, the primitives and the `RpcDecision*` types are emitted only when a method declares a decision.

## Method requirements and UI gating

`rpcMethodInfo` holds, for every method, what the schema says before the method is called — exported from the
handler's own declarations, so the UI never repeats them:

| Field | From |
| --- | --- |
| `requires.anonymous` | `[AllowAnonymous]` |
| `requires.authenticated` | any requirement, or an `[ElarionAuthorizationDefaults]` in scope |
| `requires.permissions` / `requires.roles` | `[RequirePermission]` / `[RequireRole]` (all required) |
| `requires.serverChecks` | `[RequirePolicy]`, `[RequireClaim]` or `[RequireResource]` — only the server can tell |
| `readOnly` | the request is an `IQuery` |
| `idempotent` | `[Idempotent]` |
| `tags` | `[ClientTag(key, value)]` hints, e.g. `[ClientTag("timeout", "180s")]` |

Pair it with `canCall` from `@swimmesberger/elarion-contributions` to grey out an action the current user cannot
call, without naming the permission at the call site:

```tsx
import { canCall } from '@swimmesberger/elarion-contributions'
import { rpcMethodInfo } from './generated/rpc-client'

const decision = canCall(rpcMethodInfo['invoices.approve'], capabilities)   // the session capabilities
<Button disabled={!decision.allowed}>Approve</Button>
```

`canCall` returns `{ allowed: false, reason, missing? }` for the first unmet requirement (`unauthenticated`,
`permission`, `role`), or `{ allowed: true, serverChecks }`. Like a contribution's `when`, it is a UX projection:
the server authorizes every call. The same map answers other per-method questions — `rpcMethodInfo[m].tags.timeout`
for a slow operation's client timeout, `readOnly` for which actions a read-only session may still use.

## Limits, presets, sort keys and constants

Four more exports at the end of `rpc-schemas.ts` carry values the server declares, so a page shows or sends them
instead of copying them. Each is emitted only when the schema has an entry for it; `rpc-types.ts` and
`rpc-client.ts` never change. (`rpcUploadLimits`, emitted whenever params take an uploaded file, is described under
[upload limits](#upload-limits-in-the-users-language).)

| Export | What it holds | Declared by |
| --- | --- | --- |
| `rpcLimits` | Every params member's limits by method and member path, as literal types: `minLength`, `maxLength`, `minimum`, `exclusiveMinimum`, `maximum`, `exclusiveMaximum`, `minItems`, `maxItems`, and an upload member's `maxBytes`, `contentTypes` and `fileExtensions`. A nested member is reached through its parent, a list's elements through `items`. | The DataAnnotations the schema already exports, and [`[UploadLimits]`](/docs/capabilities/blob-uploads#declaring-the-limits-on-the-member) |
| `rpcPresets` | Named request values per method, each typed as the method's params. | [`[RequestPreset]`](/docs/reference/attributes#requestpreset) on the handler |
| `rpcSortKeys` | The keys the handler's sort map allows, in declaration order, with the direction a bare key applies and which one is the default. | The handler's [`SortMap`](/docs/capabilities/pagination#offset-pagination) |
| `rpcMaxSortLevels` | How many of those keys one sort may combine (`+city,-name`), per method in `rpcSortKeys`. | The same `SortMap` (`MaxLevels`) |
| `rpcConstants` | Each module's exported constants, as literal types. | [`[ClientConstants]`](/docs/reference/attributes#clientconstants) |

```ts
import { rpcConstants, rpcLimits, rpcMaxSortLevels, rpcPresets, rpcSortKeys } from './generated/rpc-schemas'

// "up to 10 receipts" and the disabled button read the server's [MaxLength(10)], typed as 10.
const maxReceipts = rpcLimits['documents.upload'].receipts.maxItems
const maxReceiptBytes = rpcLimits['documents.upload'].receipts.items.maxBytes

// A chip opens exactly the request the server counted.
const page = await rpc.invoices.list({ ...rpcPresets['invoices.list'].toTransfer, page: 2 })

// A column header toggles between +key and -key for the keys the handler allows.
const sortable = rpcSortKeys['invoices.list'].map((sortKey) => sortKey.key)
// Shift-click adds a sort level until the handler's cap (3 unless its SortMap sets MaxLevels).
const maxSortLevels = rpcMaxSortLevels['invoices.list']

const currencies = rpcConstants.billing.currencies   // readonly ["EUR", "CHF"]
```

A preset carries the members the server needs to see that request: every required member, and every other member
whose value differs from the request's default — `null` where the preset clears a default. Spread it into the params
and add the page, size or search the UI owns. Labels stay in the client's language files; the schema carries values
only. A server change to any of these reaches the client as a type change, so a page that relied on the old value
fails to compile instead of drifting.

## Params validation

The client **pre-validates request params by default** through `rpcParamsSchemas`, before anything
touches the wire. A tier-1 violation — a too-long name, a malformed email — throws a local
`RpcParamsValidationError` (carrying the method name and the underlying Zod error) instead of costing
a round trip; batch items are validated the same way. Because the schemas are generated from the same
attributes the server enforces, a request that passes the pre-flight can only fail server-side on
business rules (which come back as field-keyed validation errors using the same wire-named paths).
Set `validateParams: false` to opt out when another layer owns input validation.

`RpcParamsValidationError.fieldErrors` groups the Zod issue messages by field path in the server's
[`fieldErrors` notation](/docs/concepts/validation#field-keyed-errors) — member names joined with `.`, array
indexes as `[i]` (`"lines[1].sku"`), `""` for the params object itself — so one form helper marks fields for
a local failure and for a server validation error alike. `cause` still carries the Zod error.

```ts
function fieldErrorsOf(error: unknown): Record<string, string[]> | undefined {
  if (error instanceof RpcParamsValidationError) return error.fieldErrors
  if (error instanceof RpcError && error.isInvalidParams) {
    return (error.data as { fieldErrors?: Record<string, string[]> } | undefined)?.fieldErrors
  }
  return undefined
}
```

## Result validation

Result validation runs by default through `rpcResultSchemas`. Use `transformResult` for app-specific
normalization before validation, or set `validateResults: false` when another layer validates
responses.

## Tracing with OpenTelemetry

The client stays OpenTelemetry-package-free — it never imports a tracing SDK. To make a call appear in a
distributed trace, pass an `instrumentation` adapter that starts a span per request/batch and injects the W3C
`traceparent` header. An ASP.NET Core host running OpenTelemetry with `AddAspNetCoreInstrumentation()` extracts
that header, so the server request span, the JSON-RPC dispatch, and the handler-pipeline spans all nest **under
your client span** — one end-to-end trace.

Implement `RpcInstrumentation` over `@opentelemetry/api`:

```ts
import { context, propagation, trace, SpanKind, SpanStatusCode } from '@opentelemetry/api'
import { createRpcApi, type RpcInstrumentation } from './generated/rpc-client'

const instrumentation: RpcInstrumentation = {
  startSpan(ctx) {
    const span = trace
      .getTracer('rpc-client')
      .startSpan(ctx.batch ? 'rpc batch' : `rpc ${ctx.methods[0]}`, { kind: SpanKind.CLIENT })

    // Inject traceparent for this span into the headers the client is about to send.
    const headers: Record<string, string> = {}
    propagation.inject(trace.setSpan(context.active(), span), headers)

    return {
      headers,
      setError: (error) => {
        span.recordException(error as Error)
        span.setStatus({ code: SpanStatusCode.ERROR })
      },
      end: () => span.end(),
    }
  },
}

const rpc = createRpcApi({ url: '/rpc', instrumentation })
```

`RpcRequestContext` gives you `methods` (one per call, several for a `$batch`) and a `batch` flag for span
naming; the span's `headers` are applied **last**, so trace propagation stays authoritative over your static or
dynamic `headers`. The adapter above is the only Elarion-specific piece — wire the rest of the browser SDK
(`WebTracerProvider`, an OTLP exporter, `ZoneContextManager`) as shown for the
[HTTP client](/docs/capabilities/transports/openapi#trace-client-requests-with-opentelemetry), and see
[Telemetry & observability](/docs/capabilities/telemetry) for the server side.

## Handlers exposed only over REST

The generator reads `rpc-schema.json`, and that schema lists the operations the JSON-RPC transport serves —
handlers carrying `[Handler]` with `HandlerTransports.JsonRpc`. A handler that carries only
[`[HttpEndpoint]`](/docs/capabilities/transports/http-endpoints) (a public link answered without a session, a
route that must live outside `/rpc`, an endpoint for third-party callers) is not on the JSON-RPC bus, so the
generated client has no function, no types, and no Zod schemas for it.

That is deliberate. REST's machine-readable contract is the **OpenAPI document**, and Elarion leaves REST client
generation to the off-the-shelf OpenAPI tooling instead of owning a second, bespoke HTTP client generator
([ADR-0026](https://github.com/swimmesberger/Elarion/blob/main/docs/decisions/0026-openapi-http-transport.md)). Folding
routes, verbs, and route/query/header/body binding into `rpc-schema.json` would make this generator re-implement
what OpenAPI already describes and what those tools already consume. Pick one of two paths instead — never
hand-copy the response DTO into a Zod schema, because a C# rename then still compiles and silently breaks the page:

- **The operation does not need to be a REST route.** Add `[Handler]` next to (or instead of) `[HttpEndpoint]`.
  It joins `rpc-schema.json` and gets the generated function, params/result Zod schemas, and the typed
  [error union](#error-handling) for its declared codes. Authorization and validation stay on the handler, so an
  anonymous handler stays anonymous on either transport.
- **It must stay REST-only.** Add `Elarion.AspNetCore.OpenApi`, export the document, and generate a client from it —
  the [recommended setup](/docs/capabilities/transports/openapi#generate-a-typed-client) uses `@hey-api/openapi-ts`
  with its Zod plugin for typed params and runtime-validated responses. Errors arrive as RFC 7807 ProblemDetails
  with the same stable `code` and `data` members as an `RpcError`; the OpenAPI document declares both, so
  [branch on `error.code`](/docs/capabilities/transports/openapi#typed-errors) without a cast.

Both clients run side by side: the JSON-RPC client for the operation-shaped API, the OpenAPI-generated one for the
handful of REST-only routes. Regenerate each from its own contract file in the same build step.

## Design boundaries

The generated runtime stays framework-neutral: it uses standard `fetch`, accepts an injected
transport and `AbortSignal`, validates with Zod, and supports batching — but never imports React,
TanStack, Vite, or any downstream framework. Applications own the adapter layer: server functions,
auth forwarding, UI-framework hooks, and result normalization wrap `createRpcApi(...)` rather than
replacing the transport.

The one exception is an **opt-in** framework adapter (`--framework tanstack-start`), emitted as a separate
`start-adapter.ts` that the core client never imports. A consumer that does not pass the flag gets
byte-identical, framework-free output — the neutrality boundary is about what the core client pulls in, not
about whether a separate opt-in file may exist.

<Callout type="warn">
  The generator interprets the framework's schema format and does not support arbitrary JSON Schema
  composition. `anyOf` is supported in the shape the server exports for [C# unions](#c-unions-map-to-typescript-unions);
  `oneOf` and `allOf` are rejected — adjust the exported DTO shape or extend the generator deliberately. Re-run the generator whenever `rpc-schema.json` changes, or
  the frontend types go stale.
</Callout>
