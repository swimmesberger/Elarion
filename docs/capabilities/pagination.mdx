title: Pagination
description: Transport-neutral keyset (cursor) and offset paging that produces a Page<T> or an OffsetPage<T>, with multi-key sorts and an opaque cursor codec.
---

A list handler returns one of two transport-neutral envelopes (from `Elarion.Abstractions.Paging`), each the same
across JSON-RPC, MCP, HTTP, and the generated TypeScript client — `Page<T>` for a keyset list, `OffsetPage<T>` for a
numbered one:

```csharp title="Elarion.Abstractions.Paging"
public sealed record Page<T> {                    // keyset: ToKeysetPageAsync
    public required IReadOnlyList<T> Items { get; init; }
    public string? StartCursor { get; init; }
    public string? EndCursor { get; init; }
    public bool HasNext { get; init; }
    public bool HasPrevious { get; init; }
    public int? Total { get; init; }             // only when a handler counts
}

public sealed record OffsetPage<T> {              // offset: ToOffsetPageAsync
    public required IReadOnlyList<T> Items { get; init; }
    public required int Total { get; init; }
    public bool HasNext { get; init; }
    public bool HasPrevious { get; init; }
}
```

The cursors follow the Relay convention: `StartCursor`/`EndCursor` are opaque tokens for the first
and last items. Offset paging always counts and never has cursors, so its envelope says exactly that: `Total` is
required and the generated TypeScript type is `{ items, total: number, hasNext, hasPrevious }`. `Page<T>.Empty` and
`OffsetPage<T>.Empty` (with `Total = 0`) are ready-made empty pages, and `offsetPage.ToPage()` converts an offset page
for an endpoint whose contract stays `Page<T>`.

Keyset (seek) pagination is the default for feeds and large lists; offset pagination is available
where a UI needs page numbers and a total count.

<Callout type="info">
  Pagination ships in a **separate package** (`Elarion.Paging`) so the EF Core marker package stays
  dependency-free. The execution helpers depend on EF Core (`Microsoft.EntityFrameworkCore.Relational`),
  while the provider-neutral `Page<T>` and `OffsetPage<T>` envelopes and the `IKeysetPageRequest`/`IOffsetPageRequest`
  contracts live in `Elarion.Abstractions.Paging`. Reference `Elarion.Paging` (the runtime helpers) and
  `Elarion.EntityFrameworkCore` (which bundles the generator that emits keyset definitions) in the
  project that owns your entities and handlers:

  ```xml
  <PackageReference Include="Elarion.Paging" Version="0.4.6" />
  <PackageReference Include="Elarion.EntityFrameworkCore" Version="0.4.6" />
  ```
</Callout>

## Keyset pagination

Declare the ordered key columns on a dedicated partial class with `[Keyset<TEntity>]` — the entity
stays free of pagination concerns, and an entity can have any number of orderings. Columns are
ascending by default; prefix a name with `-` for descending. The generator
([`KeysetGenerator`](/docs/concepts/source-generation)) fills the class with a reflection-free
`IKeysetDefinition<TEntity>` (ordering and seek predicate are plain typed expressions the provider
translates to SQL like hand-written `OrderBy`/`Where`) plus a static `Definition` singleton and an
opaque cursor codec that carries the key values (no extra round-trip to reload a reference row):

```csharp
using Elarion.Paging;                 // [Keyset<T>]

public sealed class Client {
    public Guid Id { get; init; }
    public DateTime CreatedAt { get; init; }
    public string Name { get; init; } = "";
}

// one partial class per ordering, declared near the feature that pages it
[Keyset<Client>(nameof(Client.CreatedAt), nameof(Client.Id))]   // CreatedAt, then Id to break ties
public sealed partial class ClientsByCreated;
```

For a "newest first" feed, prefix each column with `-` to sort descending. Keeping every column the
same direction also lets the Npgsql provider use a row-value seek (see below):

```csharp
[Keyset<Post>("-CreatedAt", "-Id")]   // CreatedAt desc, then Id desc to break ties
public sealed partial class RecentPosts;
```

Handlers call `ToKeysetPageAsync` with the keyset definition and a server-side projection. Passing
the definition explicitly (`ClientsByCreated.Definition`) keeps keyset symmetric with offset paging —
which passes a `SortMap` — and lets one handler choose among an entity's orderings. The request
implements `IKeysetPageRequest`, so its `After`/`Before`/`Size` fields stay flat for HTTP GET query
binding (`KeysetPageRequest` is a ready-made implementation for handlers that need no extra filters):

```csharp
[Handler("clients.list")]
[HttpEndpoint("clients")]
public sealed class ListClients(AppDbContext db, ICurrentUser user)
    : IHandler<ListClients.Query, Result<Page<ListClients.Item>>> {

    public sealed record Query : IKeysetPageRequest {
        public string? After { get; init; }
        public string? Before { get; init; }
        public int Size { get; init; } = 20;
        public string? Search { get; init; }
    }

    public sealed record Item(Guid Id, string Name, DateTime CreatedAt);

    public async ValueTask<Result<Page<Item>>> HandleAsync(Query query, CancellationToken ct) {
        var rows = db.Clients.Where(c => c.OwnerId == user.UserId);
        if (!string.IsNullOrEmpty(query.Search)) {
            rows = rows.Where(c => c.Name.Contains(query.Search));
        }

        return await rows.ToKeysetPageAsync(
            query,
            ClientsByCreated.Definition,
            c => new Item(c.Id, c.Name, c.CreatedAt),
            maxSize: 100, ct);
    }
}
```

The `selector` is the only projection — it runs server-side, composed with the key columns so the
query reads just your columns plus the keys (untracked, no extra round-trip) and encodes the boundary
cursors from those keys. That is why it is passed in rather than applied as a separate `.Select`
before paging: the cursor needs the key values your DTO does not carry.

Pass `After` (an `EndCursor` from a prior page) to page forward, `Before` (a `StartCursor`) to page
backward, or neither for the first page. `Size` is clamped to `maxSize` (defaulting to
`QueryablePagingExtensions.DefaultMaxSize`, which is `100`).

<Callout type="warn">
  Cursors are opaque but **not** a security boundary — they encode the boundary row's key values and
  are neither signed nor encrypted. Keep applying your own authorization filter (e.g.
  `Where(c => c.OwnerId == user.UserId)`); never trust a cursor for access control.
</Callout>

Each cursor embeds a build-stable **keyset-identity tag** (a hash of the definition's fully-qualified
name and its ordered column types), so a cursor minted by one keyset endpoint is rejected — not
silently reinterpreted — when fed to another. A cursor that is malformed, truncated, of the wrong
format version, or carries a mismatched identity tag makes `BuildSeek` (and therefore
`ToKeysetPageAsync`) throw a `MalformedCursorException` rather than resetting to the first page.
Map it to a validation / `400 Bad Request` response so the client learns its cursor is invalid; its
message names no key values and is safe to surface.

### Keyset column rules

The generator enforces the hard column rules at compile time, so a typo or a column that cannot be
translated is a **build error**, not a runtime bug:

- Column names must match a property (`ELKEY001`, error), so a typo — or a rename you forget to
  propagate — fails the build. That is why the `"-Column"` string form needs no `nameof`.
- Columns must be **non-nullable** (`ELKEY003`, error) for deterministic SQL ordering.
- If the entity has a primary-key property that is not part of the keyset, the generator **warns**
  (`ELKEY004`) that paging may skip or repeat rows; append it (or another unique column). The key is
  detected as a `[Key]`-annotated property, or the EF conventional name `Id` or `{EntityType}Id`. It
  stays a warning rather than an error because a keyset whose own columns are already unique is
  legitimately deterministic without the key.
- Supported column types are the integral types (`int`, `long`, `short`, `byte`),
  `decimal`/`double`/`float`, `string`, `Guid`, `DateTime`, `DateTimeOffset`, `DateOnly`, `TimeOnly`,
  and enums; others report `ELKEY002`.
- The keyset class must be a **top-level, non-nested partial class** (`ELKEY005`) so the generator can
  emit the definition into it.

### Provider-optimized seek (Npgsql row values)

By default the seek predicate is a portable lexicographic comparison
(`a > x || (a == x && b > y)`) that every provider can translate. PostgreSQL can do better: a
[row-value expression](https://www.npgsql.org/efcore/release-notes/7.0.html#row-value-expressions)
`(a, b) > (x, y)` is a single comparison that a composite index on `(a, b)` satisfies directly. EF
Core has no provider-neutral row-value API yet ([dotnet/efcore#26822](https://github.com/dotnet/efcore/issues/26822)),
so this is an explicit opt-in that keeps the default output provider-neutral.

Add the assembly-level attribute (typically in the project that owns your entities) to switch the
generated seek to row values:

```csharp
using Elarion.EntityFrameworkCore;

[assembly: UseElarionEntityFrameworkCore(Provider = EfCoreProvider.Npgsql)]
```

With `Npgsql` selected, a keyset of two or more columns (up to seven) that share one direction emits
`EF.Functions.GreaterThan`/`LessThan` over `ValueTuple`s, which Npgsql renders as a row value:

```csharp
// [Keyset<Client>(nameof(Client.CreatedAt), nameof(Client.Id))] with the Npgsql provider:
__e => EF.Functions.GreaterThan(
    ValueTuple.Create(__e.CreatedAt, __e.Id),
    ValueTuple.Create(__key0, __key1));
```

The generator falls back to the portable predicate automatically when row values do not apply: a
single-column keyset, mixed sort directions (e.g. `-CreatedAt, Id`), a keyset of more than seven
columns, or the default `Portable` provider. The opt-in requires the
`Npgsql.EntityFrameworkCore.PostgreSQL` package, which supplies the
`EF.Functions.GreaterThan(ValueTuple, ValueTuple)` overloads the generated code calls.

## Offset pagination

When a UI needs random page access and a total count, use `ToOffsetPageAsync`, which returns an `OffsetPage<T>`,
with a `SortMap` — an
AOT-safe whitelist that binds sort keys to typed selectors (no dynamic LINQ, and clients can only sort
by columns you allow). Each entry may chain `ThenBy` tiebreakers (each with a `SortDirection`) for a
stable composite order. The map is a fixed whitelist that doesn't depend on the request, so build it
once with `CreateBuilder(...).Add(...).Build()` and keep the immutable result in a `static readonly`
field rather than rebuilding per call:

```csharp
private static readonly SortMap<Client> Sort = SortMap<Client>
    .CreateBuilder("createdAt", c => c.CreatedAt, SortDirection.Descending)   // default sort
    .ThenBy(c => c.Id, SortDirection.Descending)                             // stable tiebreaker
    .Add("name", c => c.Name)
    .ThenBy(c => c.Id)
    .Build();

public async ValueTask<Result<OffsetPage<Item>>> HandleAsync(Query query, CancellationToken ct) {
    return await db.Clients
        .Where(c => c.OwnerId == user.UserId)
        .ToOffsetPageAsync(query, c => new Item(c.Id, c.Name, c.CreatedAt), Sort, maxSize: 100, ct);
}
```

The request implements `IOffsetPageRequest` — flat `Page` (1-based), `Size`, and `Sort` fields, again
to keep HTTP GET query binding simple (`OffsetPageRequest` is the ready-made implementation).
`Build()` produces an immutable map backed by a `FrozenDictionary`, so a shared static instance is
safe for concurrent requests; the mutable `SortMapBuilder` is single-threaded and used only at
startup.

A request `Sort` names a key in one of three forms:

| `Sort` | Primary column | Tiebreakers |
| --- | --- | --- |
| `key` (bare) | the entry's **declared** direction | declared |
| `+key` | ascending | declared |
| `-key` | descending | declared |

A bare key is **not** "ascending": `"createdAt"` above sorts descending, because that is how the key was declared,
and a client that wants it ascending sends `"+createdAt"`. `"-name"` sorts `Name` descending, `Id` ascending. Keys
match case-insensitively. A blank `Sort` means the default entry. In a query string, send `+` as `%2B`: a bare `+`
decodes to a space, which leaves the key bare.

### Sorting by several keys

`Sort` may list several keys, comma-separated, each in one of the three forms: `"+city,-name"` orders by `City`
ascending, then `Name` descending. The keys apply from left to right (`OrderBy`, then `ThenBy`), and the declared
tiebreakers of the **last** key follow, so the order stays stable; the tiebreakers of the other keys are not applied.
A single key keeps its own tiebreakers, as before. Spaces around a key are ignored.

A sort combines at most `SortMap<T>.DefaultMaxLevels` (3) keys; `.MaxLevels(n)` on the builder changes the cap, and
`.MaxLevels(1)` allows a single key only. A key named twice, an empty key (`"city,"`) and a sort above the cap are
refused like an unknown key. The cap is checked before any key is looked up, so a sort parameter of thousands of keys
costs one pass over the text. The schema exports the keys, not the cap; a client that combines more keys than the
handler allows gets the validation error below.

### Refusing a bad sort

An **unknown** key also falls back to the default entry — right for a list that must always render, wrong when a
client sends a key it should not. `Sort.Validate(query.Sort)` checks the sort first and answers a refused one (an
unknown or repeated key, or more keys than the cap) with a field-keyed validation error (code
`paging.sort_key_unknown`, keyed by the request field, naming the allowed keys), so the client bug surfaces instead of
a silently re-sorted list:

```csharp
[ProducesError(PagingErrorCodes.SortKeyUnknown, ErrorKind.Validation)]
public async ValueTask<Result<OffsetPage<Item>>> HandleAsync(Query query, CancellationToken ct) {
    if (Sort.Validate(query.Sort) is { } unknownSort) return unknownSort;

    return await db.Clients
        .Where(c => c.OwnerId == user.UserId)
        .ToOffsetPageAsync(query, c => new Item(c.Id, c.Name, c.CreatedAt), Sort, maxSize: 100, ct);
}
```

The default message is English. Pass a `message` function to word it yourself, for example in the application's
language; it receives a `SortRefusal` with the `Reason` (`UnknownKey`, `RepeatedKey`, `TooManyKeys`), the offending
`Key`, the `AllowedKeys` and `MaxLevels`, and its text becomes both the error message and the field message:

```csharp
if (Sort.Validate(query.Sort, message: refusal => refusal.Reason switch {
        SortRefusalReason.TooManyKeys => $"Höchstens {refusal.MaxLevels} Sortierschlüssel.",
        _ => $"Unbekannter Sortierschlüssel „{refusal.Key}“."
    }) is { } badSort)
    return badSort;
```

`Sort.Keys` lists every allowed key in declaration order with its declared direction and which one is the default —
what a client needs to build sort parameters (a column header toggling between `+key` and `-key`) without mirroring
the declarations by hand. The [JSON-RPC schema](/docs/capabilities/transports/schema-generation) exports them under the
method's `sortKeys` when the handler declares one static `SortMap` field (with several it exports none and the build
warns, `ELRPC012`), and the generated TypeScript client gives them as `rpcSortKeys['{method}']`, so a frontend reads
the allowed keys instead of copying them.

### Mapping a page

`Map(selector)` on a `Page<T>` or an `OffsetPage<T>` projects every item and keeps the cursors, flags and total, so
enriching or renaming the rows of a page never rebuilds the envelope by hand. `MapAsync` hands the whole item list to the selector at once —
one batched lookup for the page instead of one per row — and requires one result per item, in order:

```csharp
var page = await db.Notes.ToOffsetPageAsync(query, n => new { n.Id, n.Text, n.AuthorId }, Sort, maxSize: 50, ct);
return await page.MapAsync(async (rows, token) => {
    var authors = await directory.GetNamesAsync(rows.Select(r => r.AuthorId).Distinct(), token);
    return rows.Select(r => new NoteRow(r.Id, r.Text, authors[r.AuthorId])).ToArray();
}, ct);
```

### Consuming an offset page

An offset endpoint returns `OffsetPage<T>`, so the client gets exactly what it can use:

- `total` is **always present** (`ToOffsetPageAsync` counts the filtered query every call), and the generated type
  says so (`total: number`), so page numbers are computable: `totalPages = Math.ceil(total / size)` — where `size` is
  the **effective** page size, not necessarily the one you sent.
- There are no cursors to ignore.
- `hasNext` / `hasPrevious` are filled on both strategies, so a plain prev/next control needs nothing
  else.

The effective size matters because the server clamps `Size` to the handler's `maxSize` (default `100`,
as described under [keyset pagination](#keyset-pagination) — the same clamp applies to both strategies),
and substitutes `20` for anything below `1`, itself capped at `maxSize` (so a handler with
`maxSize: 10` substitutes `10`). `OffsetPage<T>` does not echo the size back, so divide by the size the server
would actually have used, or the last page number is wrong whenever a client over-asks:

```ts
// Mirror the handler's maxSize; the server clamps and the envelope never reports what it used.
const MAX_SIZE = 100
const requested = 20
const size = Math.min(requested < 1 ? 20 : requested, MAX_SIZE)

const page = await rpc.clients.list({ page: 1, size, sort: '-createdAt' })

// Offset endpoint: `total` is always a number.
const totalPages = Math.ceil(page.total / size)

renderRows(page.items)
renderPager({ totalPages, canPrev: page.hasPrevious, canNext: page.hasNext })
```

The simplest way to stay honest is to never send a size above the handler's `maxSize` in the first
place — then requested and effective size are the same number.

The two envelopes share `items`, `hasNext` and `hasPrevious`, so one list component can render either; each adds only
what its strategy fills. A component that takes both reads `total` where it is a number and the cursors where they are
strings. If you find yourself wanting a cursor on an offset endpoint, you are on the wrong strategy — switch the
handler to `ToKeysetPageAsync`.

### Naming the request fields

`IOffsetPageRequest` fixes three member names — `Page`, `Size`, `Sort` — and the execution helpers read
the request through that interface. Those names reach the wire through your DTO, so a request that
implements the interface publishes `page` / `size` / `sort`.

If a contract needs different wire names (`pageSize`, say, or a `sortBy`/`sortDirection` pair), do not
rename the interface members — a request DTO owns its wire contract, and the paging contract is not the
place to negotiate it. Carry your own fields and build an `OffsetPageRequest` inside the handler:

```csharp
public sealed record Query {
    public int Page { get; init; } = 1;
    public int PageSize { get; init; } = 20;          // this endpoint's own wire name
    public string? SortBy { get; init; }
    public bool Descending { get; init; }             // this endpoint's own wire shape
}

public async ValueTask<Result<OffsetPage<Item>>> HandleAsync(Query query, CancellationToken ct) {
    var paging = new OffsetPageRequest {
        Page = query.Page,
        Size = query.PageSize,
        Sort = query.Descending ? $"-{query.SortBy}" : query.SortBy,
    };

    return await db.Clients
        .Where(c => c.OwnerId == user.UserId)
        .ToOffsetPageAsync(paging, c => new Item(c.Id, c.Name, c.CreatedAt), Sort, maxSize: 100, ct);
}
```

The translation is three lines in one place, and the endpoint keeps the vocabulary its clients expect.
